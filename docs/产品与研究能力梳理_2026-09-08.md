# 产品与研究能力梳理

日期：2026-09-08。状态：讨论与梳理中，仅授权记录文档，尚未授权实施。

## 目的与边界

以 Vibe-Deep-Research fork 为后续产品基底，利用现成桌面、行情和交互，尽快验证自己的研究思路。Stock-Research Backend 继续提供现有服务，当前不修改该仓库、不迁移整套 Backend。

用户正在从实际使用体验判断功能取舍。本文记录已确认方向、源码观察和待讨论问题，不是实施计划；旧项目方案、上游决定和助手建议不能自动升级为本 fork 的决定。

用户已反馈 Backend 问题修复、最新研究轨迹已运行；这是用户提供的当前状态，不是本次文档工作重新执行的验收。

## 方向一：补齐 Wiki 知识能力

**用户判断**：上游当前应该没有集成我们需要的 Wiki，这是本次梳理的重要方向。

**已查到的实现**：上游已有公司知识归档。`orchestrator/src/knowledge.ts` 从经过校验的阶段产物生成公司运行档案和 `latest.md`，下次按日期及有效天数召回；另有资料库检索与引用能力。因此不能描述成“没有知识或证据能力”。目前检查的路径尚未显示它已接入 Stock-Research 的 Wiki；公司档案也不等同于我们定义的编译知识页。

**讨论基础**：Stock-Research Wiki 承载有依据的编译知识，区分来源披露、事实与研究判断，refs 可下钻到固定版本的原文 Block。Backend 继续拥有正式存储、校验与发布；前端呈现和 Agent 消费方式待讨论。

**待确定**：

- Wiki 在公司、行业页面及聊天中怎样被发现、阅读和引用。
- 现有公司档案、研究记录和资料库分别保留什么职责，避免形成重复知识写入入口。
- 首轮只读取还是同时接入维护草案，以及用户如何查看差异、确认更新。

源码参考：[知识归档](../orchestrator/src/knowledge.ts)、[资料库](../orchestrator/src/report_library.ts)。

## 方向二：引入 DSH 改善 Agent 体验

**用户提出的方向**：实际使用上游 Agent 后体验不好，认为可以直接引入 DSH。将引入 DSH 作为重要架构讨论方向，不再默认沿用上游 Agent 实现。

**尚未拍板的内容**：接入方式、替换范围、实施顺序，以及是否调整现有聊天、六阶段研究、模型接入和桌面进程管理。此前助手提出“首轮不接 DSH、沿用现有 Agent”的方案仅为候选，未获确认，不构成约束。

**待确定**：

- 将实际体验问题拆开：取材与推理、工具组合、上下文、任务连续性、耗时或交互分别有什么问题。
- 哪些问题由 DSH 运行与插件机制解决，哪些仍属于研究方法、Backend 能力或产品设计。
- 如何保留已可用的桌面与行情，并让 Agent 经工具消费 Stock-Research 服务。
- 上游运行时哪些入口保留、替换或退出，避免两个运行时同时拥有同一个研究任务。

源码参考：[现有工具桥接](../orchestrator/src/assistant_bridge.ts)、[Agent 对话入口](../orchestrator/src/assistant_turn.ts)。引入 DSH 并不自动证明研究质量改善，后续需以相同业务问题检验。
