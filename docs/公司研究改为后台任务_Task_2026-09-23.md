# 公司研究改为后台任务

状态：2026-09-23 用户确认；S1 已完成并审阅通过（§9.1a）；DSH 0.1.7 已切换（`baseline/dsh-0.1.7-alpha.2`），[研究沉淀整理修复](研究沉淀整理修复_Task_2026-09-23.md) 已完成。S2 已实施；2026-09-24 连同[公司研究任务修复](公司研究任务修复_Task_2026-09-24.md)由用户以海螺水泥完成真实流程验收（研究 → 整理 → 结果），已提交。执行方不做浏览器或真实流程测试；不提交、不 push。执行记录见 §9.2。

权威：[Human Checklist](../human-checklist.md)「公司研究是后台任务，不是深度对话（2026-09-23）」；报告子 Agent 先例见 [M9.5 E 节](公司Wiki生成与交互报告_Task_M9.5_2026-09-17.md)；对象与动作模式见[产品对象模型与交互 v1](产品对象模型与交互_v1_2026-09-23.md) §3.2。

## 1. 问题

个股页「开始 / 继续研究」现在以普通深度对话会话执行（`dsh/client.tsx` `research.start(question, company)` → `client.sessions.create` + 标题 `公司研究 · <代码> · <名称>`），因此：会话出现在深度对话历史与最近对话；个股页研究中横幅提供“查看执行对话”（`pages/CompanyWiki.tsx` 约 271、340 行），点开跳进深度对话；失败文案“可以查看执行对话后重试”（约 178 行）。用户认为产品定位错位：公司研究是后台任务，与深度对话无关。

## 2. 目标与冻结决定

- 公司研究作为**后台任务**执行：复用报告任务的“隐藏任务宿主 + `ctx.subagents.start('spawn')` 子 Agent + 绑定文件”机制（`desktop/dsh/finance-ui/host-state.mjs` `startReportRun` / `ensureTaskHost`，Stock `research-tools.mjs` 按绑定文件判定角色）。不新增执行器或第二套会话存储。
- 不出现在深度对话、最近对话与历史列表；可在「我的研究 · 任务」以只读过程查看（本 Task 复用现有 `openTaskProcess`，新增任务类型如 `research`；过程视图随后在 T3 统一为原生对话的只读模式，本 Task 不重做过程面板样式）。
- 个股页横幅：只保留“查看任务记录”；去掉“查看执行对话”；失败文案改为指向任务记录。横幅之外的等待效果沿用新建研究页的加载效果（T2 动作模式）。
- 研究角色与工具集不变（`deep_research` 研究能力 + 绑定当前公司为维护目标）；首问文字沿用[深度对话提示词 Task](深度对话提示词与文案收敛_Task_2026-09-23.md) A 批的人话版本。
- **研究结束后的知识整理必须照常发生**：研究页的草案 / 回读链路不能因为改为子 Agent 而断掉（见 §3 S1-2）。
- 同一公司同时只允许一个研究任务在跑（沿用现有 `companyStarts` 去重语义，迁到任务层）。
- 旧的 `公司研究 · …` 深度对话会话：不删除、不改写；从深度对话历史与最近对话中隐藏，并可在任务记录中以只读过程打开。

## 9. 执行回填

### 9.1 S1 核对（2026-09-23，只读；待审）

**结论：可以复用一个隐藏任务宿主，但不能只把公司研究改成现有报告 `spawn`。** 子会话目前被 `skipWikiReviewFor` 排除在后台整理外；即使研究回合的 `finalizeTurn` 仍运行，也不能据此承诺生成 Wiki 草案。建议研究结束后由 Stock 的同一整理 Owner 捕获该回合快照，以隐藏宿主为父节点启动一次**同级**「知识整理」子任务；公司研究任务与整理结果保留明确来源关联。S2 前须审定此接法，不能以页面轮询替代整理执行。

1. **宿主、并发与身份。** Vibe `host-state.mjs:166-169,202-230,411-499` 的 `spawnChain` 串行化启动，`pending` 只覆盖 spawn 前的短窗口（15 秒过期），`reportRuns` 则跟踪整次运行；因此单个宿主并不把报告和研究的**执行期**串行化。现有 `report-tasks.json` 同时保存宿主、会话绑定和一个无类型 `pending`（`host-state.mjs:114-120,153-157`）；Stock `research-tools.mjs:98-118,153-160` 会把同宿主的 pending 子会话直接认作 `wiki_report`。采用**同一绑定文件、显式 `kind: report | research`**，旧记录缺 kind 视为 report；`pending` 也带 kind，并在同一启动锁下跨类型互斥。Stock 只按绑定识别角色；研究绑定另存公司 slug，作为 `deep_research` 的 `boundTarget`。独立 `research-tasks.json` 会形成第二个 pending/宿主协调点，当前没有必要。这里还需验证绑定在首个模型请求前生效，以及报告、研究同时启动不串角色。
2. **模型、中止、重启。** 报告每次从 DSH 默认选择 provider/model/reasoning effort，空宿主不继承模型（`host-state.mjs:432-474`）；研究应复用。当前中止只找到进程内 `reportRuns`，运行时卸载会 abort 并释放 handle（`host-state.mjs:232-250,502-507`）；研究要有同等、按类型校验的控制入口。绑定文件持久化，GET 会从 DSH live/persistence 回填真实 parent（`host-state.mjs:123-143,550-575`），前端再按 parent 查询子任务目录（`client.tsx:438-466`）。重启后可读任务身份与原生日志，**不能由绑定本身推断任务成功或自动续跑**；任务列表须区分已完成、失败、取消、中断和未知，成果另以 Backend 回读确认。
3. **现有整理断点。** Stock `research-tools.mjs:132-136,203-229` 对任何 `header.parentSession` 设置 `startReview: undefined`；`research-host.mjs:37-66,80-115` 仅在成功回合、材料任务完成且无来源错误时派发复核，同时仍单独调用 `finalizeTurn`。复核实际在 `background-review.mjs:373-386,435-449,480-501` 再 `spawn` 一个子 Agent、写 Backend 草案和后台任务记录。报告研究子 Agent 使用 `maxDepth: 1`（`host-state.mjs:462-474`），安装版 DSH 的 `resolveChildDepth` 会拒绝超过上限的下一层（`desktop/dsh/runtime/node_modules/@deepseek-ai/dsh-subagent/lib/types/child-agent.js:32-39`）。因此直接放开 `skipWikiReviewFor` 会尝试深度 2；即使提高深度，研究子会话结束时 `watchReportRun` 释放 handle、Stock `agent/disposed` 清理 host（`host-state.mjs:232-238`；`research-tools.mjs:368-374`），整理生命周期也可能被取消。**不选嵌套复核。**
4. **建议接法与页面结果。** Stock 在公司研究成功结束且符合现有复核门槛时，冻结 `reviewSnapshot`、来源轮次和维护目标；由隐藏宿主作为 DSH parent 发起同级 `runBackgroundReview`，其运行/失败记录独立于研究子会话的释放和页面生命周期。保持 Stock 为唯一整理触发 Owner，Vibe 只负责宿主、任务绑定和状态读取；同一研究回合只调度一次，不让报告或普通子会话进入。现有 `background-review.mjs:389-391,455` 把 DSH parent 当作来源会话，而个股页 `research.ts:240-245` 按来源 session 查整理记录；同级方案须显式保留**实际父子身份**与**来源研究 session**两个 ID，并让页面按后者查记录及草案，不可把宿主 ID 冒充研究来源。草案由 Backend `POST /wiki/page-drafts/research` 返回未发布 token；页面现有 `CompanyWiki.tsx:185-228` 先读任务状态，再读 `pages/read` 的版本变化。出现草案时显示待确认，发布/回读后才可称本页更新；无增量、失败、超时也必须结束等待并给真实状态。备选的“放开子会话复核”需改变深度限制并解决子会话释放时的取消，改动和回归面更大，不建议。
5. **用户交互与状态映射。** `deep_research` 的工具清单没有 `review_maintenance`（Stock `consumers.mjs:44-53,127-135`）；Stock 仅给五页 Agent 模式的维护工具传 `userQuestions`（`research-tools.mjs:249-252`）。现有公司研究与知识整理不依赖子 Agent 直接提问；待确认草案仍回产品入口。当前 `client.tsx:392-437` 的 `companyStarts` 仅去重同一前端实例，`findCompanySession` 依赖旧顶层标题；要改为按公司绑定查询运行中的子任务，启动锁在宿主侧落实跨页面/重复点击去重。`CompanyWiki.tsx:155-183` 的 `sessionState` 对冷子会话可能为 null，须采用绑定 + 原生子任务目录/轨迹判断执行状态；`185-228` 的整理记录与 Backend 页面回读继续承担结果状态。旧顶层公司研究会话只在列表显示层按既有标题识别，不改持久数据。

**S2 最小改动面与验证点：** Vibe 宿主的类型化绑定、启动/中止/状态入口及公司去重；Stock 按绑定设置 `deep_research`/`boundTarget`，成功回合快照交给同级整理并保存来源 ID；前端任务列表、只读过程、旧历史隐藏和个股页状态映射。确定性验证跨类型并发与首请求角色、同公司去重、失败/取消不整理、成功后恰好一次整理、草案关联原研究 ID、重启后真实状态；再用真实 DSH/Backend 路径验证草案或页面版本回读。此节只审代码与契约，**未运行公司研究子任务，也未证明真实模型、Backend 写入或页面视觉验收**。S1 到此停止，待审后再做 S2。

### 9.1a 审阅结论（2026-09-23，Claude Code）

- **通过**：同一隐藏宿主下“公司研究 → 同级知识整理”两个子任务，不嵌套复核；单一绑定文件加 `kind: report | research`（缺省视为 report），`pending` 带类型并在同一启动锁下跨类型互斥；Stock 仍是唯一整理触发 Owner；整理记录同时保存实际父子身份与来源研究 session，页面按后者查草案；任务存在不推断成功，成果以 Backend 回读为准。
- **补充要求（并入 S2）**：
  1. 任务记录与个股页把研究与其整理显示为**一个任务、两阶段**：研究中 → 整理中 → 结果（草案待确认 / 已更新 / 无新增 / 失败 / 取消 / 中断），不向用户展示两条独立任务。
  2. 验证研究进行中用户点「刷新资料」：研究整理与确定性刷新都可能写同一研究页，确认版本校验使后到者失败可重试、不互相覆盖。
  3. S2 在 DSH 升级 S4 之后实施：子 Agent 启动、深度上限、会话保留等接口在 0.1.7 可能变化，避免适配两次；实施前对照 DSH S1 盘点结论复核本节引用的接口与行号。

### 9.2 S2 实施与自动检查（待用户验收）

**DSH 0.1.7-alpha.2 接口复核（实施前）：**

- 子 Agent 启动：已安装 `@deepseek-ai/dsh-subagent/lib/types/index.js` 的 `start(name, request)` 仍先校验 provider 能力及深度，再返回 `SubagentRun`；`request` 包含 `parent`、`signal`、`agentOptions`、`label`、`maxDepth`、`toolFilter`、`persona`。`run.id` 是本地子 session ID，`run.result` 的模型/传输失败以 `stopReason: 'error'` **兑现**，基础设施故障才可能拒绝；完成后仍须 `run.dispose()`。因此结束处理必须检查结果状态，不能仅按 Promise 兑现判成功。
- 深度上限：`lib/types/child-agent.js:32-39` 的 `resolveChildDepth` 仍以父节点深度加一，并将该**绝对深度**与 `maxDepth` 比较；空宿主的同级研究与整理各为深度 1，研究子节点下再启动整理会是深度 2，违反现有 `maxDepth: 1`。
- 会话保留：`@deepseek-ai/dsh-api-session-controller/lib/types/client/sessions/service.js:188-208` 的 `sessions.retain(target, { source, signal? })` 同步返回 `{ sessionId, binding, ready, release }`；先等 `ready` 再读 binding，用毕 `release()`。`subagentAddress(id)` 能从已加载目录取直属父子地址，`refreshProjections(id)` 是异步刷新投影。目录身份与保留引用均不代表任务成功。
- 状态读取：0.1.7 的 Session 列表投影含 `running`，且持久子会话在 live Agent 移除后保留目录项并将 `running` 置 false（`manager.js:594-627`）；服务端仍可从 live `ctx.sessions` / `ctx.agents` 与 `sessionPersistence.inspect` 读取状态及父节点。`running: false` 只表示不在运行，须结合运行结果、整理记录和 Backend 页面回读区分失败、取消、中断、无新增及成功。§9.1 的四处接口形态未改变，以上结果/状态语义已纳入 S2。

**S2 自动实施（2026-09-23）：**
