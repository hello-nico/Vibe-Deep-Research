# 版本与差异（T5）设计

状态：2026-09-23 用户确认方向（第 1、2、4 点认可；“新出现的相关材料”不单独做），待拆 Task。本文是设计决策与接口草案，不授权实施。权威：[Human Checklist](../human-checklist.md)「核心对象、数据更新与按需判断（2026-09-20）」与「版本与差异设计（2026-09-23）」；[产品对象模型与交互 v1](产品对象模型与交互_v1_2026-09-23.md) §2.4、§4.5。

## 1. 要解决的问题

议题里的判断依据了一批对象。之后数据刷新、研究更新会让这些对象变化。用户与 Agent 需要看到：**这条判断依据的对象，自上次判断以来具体变了什么**——而不是只收到“有新材料”。这是议题长期跟踪、证据墙“有变化”提示与 Jev 连续性判断的共同前提。

## 2. 决定

1. **不建全局提交体系**。各对象沿用现有版本标识，统一为“带版本引用”：研究页 `<slug>@<input_hash>`、资料 `document:<id>/<解析版本>/<sha256>`、议题 revision、研究成果 ID（不可变）、事实与关系按记录时间。不替换现有 hash / revision，不迁移数据库（延续 2026-09-20 约束）。
2. **判断记录带版本依据**：议题中每条判断保存 `basis`（带版本引用列表）与 `judged_at`。数据如何刷新，已记录的依据版本不移动。首次判断无基线时依据当前版本。
3. **按内容块对比**：研究页差异以内容块为单位给出增 / 删 / 改，附前后正文与依据变化。差异分三类，界面分开展示：
   - **研究结论**：`research_blocks`（如 `operating_model`、`industry_structure`）；
   - **数据更新**：财务、估值、经营等数字块（单独标“数据更新”，避免刷屏）；
   - **资料时间线**：新增 / 移除的来源。
4. **新材料靠刷新进入**：用户刷新资料后，新来源进入研究页资料时间线，形成新版本，自然出现在第 3 类差异中；不另做“之后新出现的相关材料”查询。不进研究页的材料（上传资料、研究关联）第一版不纳入。
5. **只提示，不代替判断**：差异不自动判定旧结论失效；是否改判断仍在议题会话中由用户与 Agent 决定并确认。Jev 连续性判断以差异为输入。
6. **提醒方式**：以议题页 / 证据墙展示为主；用户触发的刷新若改变了某议题的依据对象，任务完成提醒卡片附“影响 N 个议题”，点击跳转。不新建通知机制。
7. **不做回滚**：回滚不得抹掉历史或使引用失效，另行立项。

## 3. 接口草案（Stock Backend，实施前核实数据来源）

- `GET /wiki/pages/diff?slug=&from=<input_hash>&to=<input_hash|current>`
  → `{ slug, from, to, blocks: [{ kind, category: "research"|"data"|"timeline", change: "added"|"removed"|"modified", before, after, refs_added, refs_removed }] }`
  数据来源：Backend 发布台账（`input_hash` ↔ 内容指纹）+ Wiki 目录 Git 历史中的 `compiled_spec`（见 §6 与 T5-a）。
- `GET /wiki/research-topics/{topic_id}/basis-changes`
  → 对每条判断的每个依据：`{ ref, pinned_version, current_version, changed, summary: { research, data, timeline } }`；研究页依据可再调上一接口看细节。资料依据第一版只报“有新解析版本”，不做段落级对比。
- 议题写入判断时（现有确认写入路径）同时写 `basis` 与 `judged_at`；旧判断无 `basis` 时视为“无基线”，只显示当前内容。

## 4. 界面（依赖 T3 / T6）

- 议题页每条判断下列出依据对象：未变化 / 有变化（徽标：研究结论 · 数据更新 · 资料时间线 各计数）；展开看块级前后对照。
- 证据墙节点“有变化”角标；点击节点打开对象，面板内可切“自上次判断以来的变化”。
- 议题会话 Agent 读取 `basis-changes` 作为续研输入，不需要用户手工描述变化。
