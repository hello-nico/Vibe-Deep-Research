# 两仓开发协议

本协议由 Vibe-Deep-Research 与 Stock-Research 逐字共享；各仓 AGENTS 引用本文件。

## Checklist 当前态

- Checklist 只保存当前有效决定，原地改写，不追加历史。推翻决定直接改原条目；历史靠 Git，需要保留的长期理由写入 `docs/decisions/`。
- 固定三章：`## 两仓共享决定`、`## 本仓决定`、`## 待用户裁决`。前两章用 `###` 按 README 模块表及模块契约分组；第三章可以为空。
- 共享章用 `<!-- shared:begin -->` 与 `<!-- shared:end -->` 包住；同时约束两仓代码或行为的决定，在两仓放逐字相同全文，不用链接代替。只影响一仓的决定归该仓。
- 每条用 `- `，占 1–3 行，末尾为 `（YYYY-MM-DD 确认｜落点）`。落点为 `已实现：<契约>`、`待实施：<Task>`、`待重设计：<Task>` 或 `规则`。
- 每份最多 200 行；代码块外单行最多 300 字。不使用「以后述」「以本补充为准」「替代下文」「覆盖下文」。本仓模块或条目不得重复共享章模块或条目。
- 让用户裁决的材料（选项、推荐、对比）先写进仓库文件（Task、过程记录或决定文档）再请用户裁决；只出现在对话里的内容不作为写入依据。
- 归属不能确定、两仓版本冲突或前后矛盾时，列入待用户裁决，不由执行方合并措辞。无法压缩而不丢约束时停止对应项并报告条目及行数，不放宽上限。
- 计划中要重做的界面或流程，先把现行实现写进对应契约，再从 Checklist 删除细节，只留一行「由 Tx 重新设计」；契约无法可靠承接时保留原条目并停止对应项。
- 不变量已经覆盖的内容，Checklist 不重复记录。

## Task 规格、当前交接与过程记录

- Task 引用上层权威，不复制正文；规格为 §1–§8，派发时最多 200 行，必须有 Out of Scope 与 Stop Conditions。
- 执行方不修改规格。规划方只在两轮之间因停止条件或验收失败修订，在状态行后写 `修订 N（日期）：原因`，旧写法移入过程记录。修订后仍最多 200 行；超过两次修订或需要新设计决定时，另开 Task 并引用旧 Task。
- `## 9. 当前交接` 每轮覆盖，最多 60 行，固定六字段：状态与结论；改动文件；证据（命令、结果、替身 / 真实）；与规格的偏差及理由；未覆盖的缺口；下一步谁做什么。
- 完整命令、结果、证据等级与决策理由追加到同目录 `<Task 名>.log.md`，默认不读。Task 代码块外单行最多 300 字。
- 冻结决定依赖模型工具调用顺序、可选调用或输出格式时，必须先做同一模型至少三次真实运行并记录通过率，或在 Stop Conditions 写明「真实运行不稳定即停，改走确定性实现」。提示词文字不构成行为已成立的证据。
- 活跃 Task 在 `docs/tasks/active/`，状态由目录表示，不另建索引。收尾后移入 `docs/tasks/archived/`，归档冻结，不修改、不作为现行依据。
- AGENTS 只放长期规则，不放当次执行状态或里程碑编号。

## 门禁、钩子与审阅

- 两仓均运行 `node scripts/verify-protocol.mjs`；另一个仓库通过 `--sibling` 或 `VIBE_SIBLING_REPO` 指定，默认同级另一仓主目录，找不到即失败。
- Checklist 格式、共享同步、AGENTS 与活跃 Task 均为硬门禁；不使用报告模式绕过失败。
- 用户在两个主目录各运行 `scripts/install-hooks`，设置仓库级 `core.hooksPath scripts/hooks`；配置由同仓 worktree 共享。执行方只在临时仓库验证，不在主目录启用。
- pre-commit 只运行 verify-protocol，以及本仓存在的 verify-docs、verify-invariants；失败即拒绝提交，不运行完整测试。禁止使用 `--no-verify`。
- CI 同时检出两仓并运行门禁。私仓访问权限与托管执行能力由用户配置并在临时分支验证；执行方不读写凭据。
- Claude 审阅不以回填替代验证，合并或提交前亲自重跑全部门禁；完整测试、运行验证、视觉与人类验收分别报告。钩子与静态检查不证明真实模型或业务能力。

## 验证范围

- 执行方只跑与改动相关的检查：改到文件对应的测试，加门禁；全量测试与跨平台测试交给 CI。
- 不为验证新装运行环境；Task 确需更大范围检查时，规格须逐条写明命令。

## 收尾三问

1. 有没有以后还会被问「为什么」的决定？写入 decision。
2. 有没有会反复验证的验收？变成测试、门禁或整体验收规范用例。
3. 有没有反复犯的错？加不变量或门禁。
