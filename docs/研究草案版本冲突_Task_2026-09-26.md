## 1. 问题

公司研究结束后的知识整理把本轮结论写成研究页草案，现有流程会和自己冲突。以 2026-09-25 农业银行这次任务为例：

| 时间（本地） | 事件 |
|---|---|
| 00:28:49 | 知识整理开始，快照记下研究页 `base_input_hash` |
| 00:29:34 | 整理先调用事实抽取收尾（`finalize_agent_extractions`，写入 4 条事实）→ 后端 `enqueue_wiki_refresh` 异步刷新研究页 → 页面 `input_hash` 改变 |
| 00:30:02 | 整理用旧 hash `POST /wiki/page-drafts/research` → `409 page revision changed or requires Backend refresh`，任务显示失败 |

中际旭创（2026-09-26 10:20）的研究页在整理开始 9 秒后也被改写，同样会撞上。

即使草案生成成功，之后任何一次机器刷新（新资料入库、事实抽取、行情估值刷新）都会让草案失效：

- `research_drafts.py` `_resolve`：页面 hash 变了，就标 `base_changed`；
- `page_drafts.py` `validate_page_specs`：要求草案里的整页 spec（除 `research_blocks`、`as_of`）等于当前 spec，否则抛 `protected_page_content`。

**根因**：草案只改 `research_blocks`，但冲突判断用的是整页 `input_hash`。机器刷新时 `wiki/compiler.py` 会原样保留 `research_blocks`（约第 45 行），只改确定性内容，所以真正需要判断的只有研究块是否被别人改过。

## 2. 冻结决定

1. **冲突判断改看研究块，不看整页**：新增确定性函数 `research_blocks_hash(spec)`，对 `research_blocks` 做规范化 JSON（按 kind 排序，字段 `kind/content/refs/reviewed_as_of`）后取 sha256。研究草案请求与账本记录 `base_research_hash`（取代草案路径上的 `base_input_hash`）。**2026-09-26 修订（Codex 触发 §5 第二条后，Claude 裁决）**：页面读取接口与其他调用方的 `base_input_hash` 保持原样，它表示整页版本，用于研究阶段按版本读页（`research-material-tools.mjs`）、Topic 依据 `page:<slug>@<hash>`（`topic-tools.mjs`）、绑定页面版本（`native-research-tools.mjs`），这些不改。
2. **生成草案**（`POST /wiki/page-drafts/research`）：请求带 `base_research_hash`。当前页面的研究块 hash 与之不等时返回 409，文案改为“研究页的研究结论已被更新，请重新整理”。相等时，在**当前**页面 spec 上替换 `research_blocks` 并校验，不再要求整页 hash 一致。
3. **采用发布**（`_publish_page_draft_unlocked`）：不直接发布 token 里存的整页 spec，而是取当前页面 spec，套上草案的 `research_blocks`，按现有规则重算 `as_of`，再走 `validate_page_specs` 与 `adapter.publish`。账本 `_resolve` 的 `base_changed` 改为比较研究块 hash。token 防篡改（`record_sha256`）保持不变，仍覆盖草案存的研究块。
4. **DSH 侧**：`dsh/src/background-review.mjs` 的快照、`validateWikiUpdate`、`REVIEW_SCHEMA` 与 persona 里的 `baseInputHash` 全部改为 `baseResearchHash`，值取自快照页面的研究块 hash。hash 由 Backend 在读取页面的接口里返回：`wiki.py` 约第 1842 行**在保留 `base_input_hash` 的同时新增** `base_research_hash`（2026-09-26 修订，原写“改名”有误）。DSH 不自己算，避免两边算法漂移。只有知识整理的草案路径（快照 → `validateWikiUpdate` → `POST /wiki/page-drafts/research`）改用 `baseResearchHash`。
4a. **Pi 不改（2026-09-26 用户裁决）**：`pi/stock-research-wiki/` 是旧运行时，产品不再使用。它的草案请求仍发 `base_input_hash`，Backend 改为只接受 `base_research_hash` 后，Pi 草案会失败，这是**已接受**的后果。不改 Pi 代码与测试，也不为它做兼容；Pi 测试失败不计入本 Task 验收。
5. **不等待异步刷新**：有了第 1 条，事实抽取与草案生成的先后顺序不再影响结果，不加轮询等待。
6. 真正的冲突（两次整理先后改同一研究页的研究块）仍然 409 / `base_changed`，行为不变。
7. 已存在的待采用草案不迁移。上线后旧草案按 `base_changed` 作废，用户可重新整理（AGENTS.md：不做兼容）。
