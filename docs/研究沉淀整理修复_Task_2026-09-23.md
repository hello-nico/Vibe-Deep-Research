# 研究沉淀整理修复

状态：2026-09-23 已实施并完成真实发布读回。Claude Code 规划与验收，Codex 按本文实施并回填 §8。不提交、不 push。实施仓库为 Stock-Research `dsh/`。

权威：[Human Checklist](../human-checklist.md)「产品核心协议」（研究后的维护须形成草案、经用户确认才发布）；[公司研究改为后台任务 Task](公司研究改为后台任务_Task_2026-09-23.md)（其 S2 验收依赖本 Task）。

## 1. 问题与证据

个股研究名单的一句话经营模式全部为空：现网 15 家公司页 `research_blocks` 均为空。2026-09-23 只读诊断（万华化学那一轮）：

- 研究后“知识整理”已启动但以 `failed` 结束，错误 `Conflicting review result`，任务记录中草案与令牌为空（`.local/dsh/research/background-tasks.json`）。断点在**整理输出 → 校验**，不在“待授权 → 发布”。
- **根因**：`dsh/src/background-review.mjs` 的 `REVIEW_SCHEMA`（约第 80 行）把 `noIncrementReason` 与 `slug / baseInputHash / content / refs / rationale` **同时列为 required**，结构化输出迫使模型在写更新时也填“无新增原因”，`validateReview`（约第 171 行）随即判冲突。这是契约设计缺陷，不是偶发模型错误。
- 次要问题：模型把公司结论写到 `operating_facts`（事实块，走事实准入），而研究结论只允许写 `operating_model`（`BLOCK_KIND` / 允许集合，第 16–22 行）。现 schema 未用枚举约束块类型。
- 失败对用户不可见：研究页只显示“资料待补充”，没有任何失败提示。

## 2. 冻结决定

- 输出契约改为**显式二选一**：`decision: "update" | "no_increment"`。`no_increment` 时只需 `noIncrementReason`；`update` 时只需 `wikiUpdates`（每页一个对象）。去掉顶层 `slug / baseInputHash / content / refs / rationale` 这套与 `wikiUpdates` 重复的旧形状。
- `wikiUpdates[].kind` 用**按页面类型的枚举**（公司：`operating_model`；行业：`operating_model`、`industry_structure`），与 `BLOCK_KIND` / 允许集合同源，不在两处各写一份。
- 校验仍然严格：`decision` 与字段不匹配、块类型不在允许集合、`refs` 不在快照内，一律拒绝。**不放宽证据与目标校验**。
- 校验失败时允许**一次**纠正：把校验错误原文回给整理模型重试一次；仍失败则按现状记为 `failed`，并写清失败原因。不无限重试。
- 草案的授权、发布与保存方式不变（持久化另归 T4）。

## 3. 步骤

1. **只读摸底**：统计 `.local/dsh/research/background-tasks.json` 中全部整理记录的结果分布（成功出草案 / no_increment / failed 及错误类型），回填 §9，确认本根因覆盖多少家。
2. 改 `REVIEW_SCHEMA`、`validateReview` 与整理提示词（第 386 行）：使用 `decision` 分支，提示词说明研究结论写 `operating_model`、事实类数字不写入研究块；块类型枚举从允许集合生成。
3. 加一次纠正重试（§2），失败原因写入任务记录，供任务提醒 / 任务记录展示。
4. 测试：`update` 只带 `wikiUpdates` 通过；`no_increment` 只带原因通过；二者混填被拒；非法块类型被拒；首次校验失败 + 纠正成功产出草案；两次失败记 `failed` 且带原因。
5. 构建 Stock `dsh/dist`；重启现用 DSH 后做真实验证。
