## 已确认边界（实施与 Review 使用同一口径）

1. 按需维护适用于 Company、Industry、Theme、Comparison 四类 Wiki；不能只实现公司后宣称所有 Wiki 完成。
2. 主 Agent 负责当前回答所需读取、计算和判断；后台子 Agent 负责本轮结束后的沉淀，不让主线执行记忆整理/建档工具链。
3. 用户画像、近期重要记忆可以自动整理；用户明确纠正优先于旧推断，且可查看、编辑、删除。
4. Agent 可以判断研究关联、发现持续问题并提出 Topic 候选；正式 Topic 仍由用户采用/创建，不以提问次数自动建档。
5. 原交接版要求 Wiki 草案/确认发布；用户后补允许后台自动更新 Wiki 与已有 Topic 的研究内容，以审计和可纠正为前提，见下节。事实/硬关系准入与新 Topic 采用边界不变。
6. Topic 聚合问题、对象、材料引用和关系展示，不复制公司/行业 Wiki，也不变成一个“所有水电资料”的无问题文件夹。

## 实施后新增原则：可审计的自动研究修订

- 用户明确：不要求判断永远正确才记录；Agent 负责证据优先、中立分析与反证，人和 Agent 共同发现/纠正，用户负责是否采纳及行动。记录不等于采纳，用户确认不再是每次研究更新的前置。
- 后台可按本轮实际触及对象自动更新 Wiki 与已有 Topic 的研究内容；不新增正式 Topic，不越权改变事实/关系层。仍按需执行，不全库主动重写。
- 自动更新必须经 Backend 正式写入：对象身份、证据引用、权限和版本冲突由代码保证；校验成功不能宣称研究结论必然正确。原草案模式仍可作为预览/失败结果，但不是所有研究修订必须等人工批准。
- 同时保留当前版本与可回读修订历史：原结论/条件、新结论/条件、修订理由、证据引用及版本、来源会话/轮次、提出者/写入者、时点、替代/推翻/分歧关系；不得覆盖掉错误判断，或仅靠临时 DSH 日志充当审计。
- 用户判断、Agent 推断、已核验事实明确区分；用户反馈改变研究重点/假设，不自动把公司事实判真。已有 Topic 更新绑定真实目标，不因同主体而误改另一议题。
- 当前版本与审计记录必须一致提交；历史或版本校验失败则不宣称写入成功。重试不得重复修订，旧快照不能覆盖新判断；纠错通过新修订保留过程。
- 先复用现有 Backend Wiki/Topic 版本历史，盘点缺少哪些审计字段及接口再最小补齐；不另建执行器或事实存储。发布权限、研究角色 guard、产品状态与契约须一起调整，不能只放开工具。
- 新增验收：保存一个证据有限、明确标注推断的判断 → 用户质疑/新证据 → 后台修订 → 当前页与历史均回读；验证原判断、为何改变、证据、来源仍可追溯，用户未采纳不妨碍记录，写入失败/并发冲突不破坏历史。
- 本节在首轮实现之后确认，属于后续调整包；review 必须与下方原 Task 缺口分列。

## 记忆内容与责任

| 对象 | 应保存 | 不应保存 |
|---|---|---|
| `soul.md` | 用户稳定的研究偏好、表达偏好、明确的长期约定；条目区分明确表达与推断 | 助手人格、模型系统权限、一次性提问推断出的永久身份/持仓/风险偏好 |
| `memory.md` | 近期持续研究主线、重要纠正、未解决的关键分歧、对应 Topic/Wiki/来源会话引用 | 逐轮流水账、整段回答、工具日志、行情财务副本、无意义“已完成”记录 |

- 本项目的 `soul.md` 明确定义为用户画像；参考仓库同名 SOUL 通常是助手人格，不能照搬语义。
- 记忆是用户范围的数据，不是所有用户共享的金融知识；DSH 提供会话/来源身份，后台子 Agent 产出修订，持久写入收敛单一 Owner。
- 实施 A 步在现有存储边界内明确两文件的实际路径、用户/工作空间作用域、唯一写入服务及修订机制。默认沿 Backend 管研究语义、Client 管界面偏好；不得同时有文件、SQLite、Backend 三份可独立修改的正文。
- Markdown 是所要求的可读载体；不因此向模型开放任意文件系统，也不创建第二个记忆执行器。若现有 Owner 无法承载，按 Stop Conditions 提交具体选择。
- 每条重要记忆应能回溯来源会话/轮次、更新时点和相关对象；最少区分用户明确表达、Agent 推断、用户已纠正。元信息采用现有契约可承载的最小形式。
- 写入采用合并/替换/删除；同义内容不重复追加，已解决主线收敛到正式 Topic 引用，过时推断淘汰。用户删除/否定后不得下一轮又由旧材料自动复活。
- 用户当前明确要求优先于记忆。记忆中的研究推断不是金融事实证据，不得替代 Block/claim/正式来源；用户反馈可以改变关注点与假设，不能凭反馈把公司事实判真。
- 为总记忆、单条内容、每次召回制定可测试的容量上限；超限先合并淘汰，不能静默截断造成丢失否定条件或伪装成功。
- 无有价值增量则不写。偏好纠正可在没有原文 Block 时更新记忆；这不意味着允许无证据改写 Wiki 事实。

## 研究连续性与 Topic 候选

1. 主线获得紧凑画像、与当前问题相关的近期主线及有界 Topic 摘要；非研究闲聊无需强制调用 Topic/Wiki 工具。
2. 最近 Topic 列表是入口，不是唯一检索范围；候选形成前按主体和研究问题核对既有 Topic，必要时有界读取较早议题。
3. 连续性依据包括重复出现的研究问题、共同机制/比较维度、用户纠正及尚未解决的裁决条件。次数仅作线索，不设置“问满 N 次自动成立”。
4. 同公司不同问题不强行合并；不同公司围绕同一机制可以形成共同主线。已有 Topic 匹配时提出复用/关联，不另建同义候选。
5. 候选至少表达：具体研究问题、涉及对象、为什么构成持续主线、来源问题引用、当前缺口、与已有 Topic 的区别或复用目标。
6. 在 DSH 对话 UI 主动呈现有价值的候选建议，并在「我的研究」复用现有研究/后台结果入口持久回看；可采用、修改、忽略，采用时再走正式 Topic 路由及创建校验，重复操作不重复创建。
7. 忽略的同一候选无实质新依据不得反复推荐。对象关系展示复用现有 Wiki/Topic/实体关系入口，不重建一套图数据库。
8. 研究关联的语义由 Agent 判断并给理由；事实关系仍需证据准入。“适合比较”不能被写成供应、控制或产业链事实。

## DSH 主动反馈与建议

- 用户明确要求利用 DSH UI 的主动反馈/建议能力，不只在后台列表被动等待用户发现，也不以回答末尾“是否需要创建 Topic”的纯文本邀约代替可操作建议。
- 实施前核对实际安装版本的原生反馈/交互 API、组件与生命周期；优先复用，必要时用现有 slot 作最小业务适配。记录真实导出、源码入口及验证结果，不凭组件名称假定能力。
- 示例：展示“建议持续研究：水电公司的盈利稳定性差异”，附简短理由、涉及公司、来源问题与已有 Topic 匹配结果；提供“采用/编辑后采用/忽略”，已有匹配则建议打开或关联已有 Topic。
- 建议可在本轮后台形成有效候选后异步出现；这是 UI 状态投影，不生成伪用户消息，不唤醒主 Agent 续写，不要求用户处理后才能继续提问。
- 按来源会话/轮次归属展示；用户切换到无关会话时不把旧建议塞进新问题下，不强制跳转或抢焦点；仍可在「我的研究」找到同一建议。
- 对话建议与「我的研究」读取同一候选及处置状态；采用、修改、忽略、失败、重试在两处一致，刷新后可回读，不建第二份候选状态。
- 只主动展示有理由、可行动的新建议；同一候选更新原项，已采用或忽略的不重复弹出，无增量只保留后台记录。Wiki 待审阅等结果可以同样提供简短反馈与查看入口，不把每一步工具执行变成通知。
- 点击采用才进入正式操作，失败明确显示且保留候选；显示建议不算创建成功，前端回调不能绕过 Backend 版本、幂等与授权校验。

## 维护时机与交接协议

| 时机 | 要求 |
|---|---|
| 主线回答前/中 | 只取得当前回答所需资料；缺 Wiki 不阻塞回答，但当前结论缺证据仍须补齐或说明缺口 |
| 成功 turn/end | 同步捕获不可变快照，沿同一个 Owner 交接一次有界后台任务；不得再并行启一套“记忆复核” |
| 用户立刻追问 | 不等待后台，不向主线发维护续跑消息；已交接任务保持独立 lifetime，旧结果不得覆盖新纠正 |
| 用户后续纠正 | 在后续成功轮次形成修订输入；不得声称上一轮任务已看到尚未发生的反馈 |
| 页面打开/刷新 | 读取当前成果，不触发研究判断重写；基础数据/timeline 更新维持已有语义 |
| 子任务完成 | 保存实际产物和无增量/部分完成/失败状态，可回看；子任务完成不能再触发一轮同类沉淀 |

- 快照应包括：来源会话/轮次、本轮用户问题及相关明确反馈、最终回答、已读页面及版本、使用过的证据引用/必要原文、当前相关记忆修订、候选对象及已有 Topic 摘要。
- 最终回答只提供研究线索，不是证据；草案中的事实仍回到原始证据。禁止把全会话无限复制到后台，禁止把外部文档指令当作用户偏好。
- 触发分开判断知识增量与记忆增量：纯行情/闲聊/重复读取无增量不启动模型整理；有明确偏好纠正、连续研究新线索或有效 Wiki 增量则允许交接。
- 同一轮最多一次交接，内部按需要执行。为输入大小、读取数量、执行时间定义明确预算；超限记录可解释状态，不静默丢掉任务。
- 主线使用有界上下文快照，不在运行中的模型流重写系统提示词；后续轮次通过 DSH 支持的上下文方式读取最新相关记忆，不因后台完成自动唤醒主线。
- 多会话可同时产出；记忆写入及 Wiki 草案必须核对版本/顺序，旧快照不能覆盖用户更新，冲突保留可见结果，不能 last-write-wins 吞掉纠正。
- 每类 Wiki 均检查对象身份、原结论、适用条件与新增证据：可不变、补充、修订或记录分歧；按受影响内容更新，不用单个 operating_model 替换整页研究区。
- 多对象问题可产生多个有依据的对象更新，逐对象记录成功/无增量/缺口；不得把仅维护一个公司显示成所有目标完成。
- 无 Wiki 时允许走已授权创建草案方向；必须有对应正式接口、身份与证据。不默认从一次比较新建 Comparison Wiki，缺接口记缺口，不回退伪造已发布页。
- 「我的研究」记录来源、处理对象、记忆变更摘要、Wiki 草案、关联/Topic 候选及子会话轨迹；用户能知道改了什么、为什么、哪些没完成。
