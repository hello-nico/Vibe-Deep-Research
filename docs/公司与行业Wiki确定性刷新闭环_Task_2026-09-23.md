# 公司与行业 Wiki 确定性刷新闭环

状态：用户已授权实施；代码与定向测试已完成，真实来源和页面视觉验收待运行确认。本 Task 定义公司与行业研究页「刷新资料」的确定性检查、确认、写入和结果展示。

权威：[Human Checklist](../human-checklist.md)「产品核心协议：交互维护与 Topic 判断边界」及公司页刷新决定；[五页问助手维护闭环实施 Task](五页问助手维护闭环实施_Task_2026-09-22.md) §7.9 的行业刷新范围。Backend 拥有数据、资料时间线、任务与回执；工作台只发起、确认和展示。不经过 Agent/Jev，不改研究判断。

## 1. 问题与当前证据

- 行业刷新会先 `GET /wiki/industry-source-preview`，再 `POST /wiki/maintenance-proposals`；Backend 在两步中分别读取统计局来源。现用日志出现同一行业预览 200 后提案 409，也出现预览 422；同一容器后来能成功读取该文章和表 3 行。当前错误映射把预览的各种失败合成 `source_unavailable`，把提案阶段所有核验失败合成 `stale_source`，无法辨别临时连接失败与原文变化。单次 422 的底层异常没有日志，不能断言每次都是 TLS 故障。
- 公司 `refresh_company_api` 在确认执行时才向 Provider 取数，确认页不能展示确定的字段差异；即使全部取数失败，现实现仍可能编译、发布一次页面，并返回 `unavailable`。行业有来源 URL 去重，但没有统一的最近成功检查时间与免重复检查规则。
- 页面应允许用户离开等待中的检查；仅有实际新增/变化才展示确认。无变化、失败、部分成功和已写入必须是不同结果。

## 2. 目标与状态语义

刷新分为 **检查 → 比较 → 待确认 → 执行 → 回读**。检查只读外部来源与现有 Wiki；任何 Wiki 写入仍由用户明确确认。Backend 按 `Wiki slug + 刷新范围` 串行或合并并发检查，持久记录检查状态和结果；DSH/浏览器不另存权威刷新时间。

| 结果 | 条件与用户所见 | 后续动作 |
|---|---|---|
| 最近已检查 | 同范围最近一次**完整成功检查**距今不超过建议值 60 分钟，且目标版本未变化、没有待确认变更 | 直接返回上次检查时间与“暂无新增资料”，不访问外部来源、不弹确认 |
| 检查中 | 同对象已有检查任务 | 返回同一任务；页面可继续浏览，回到页面可读进度 |
| 无更新 | 检查成功，归一化内容与当前已发布内容一致；行业最新合格来源已在时间线 | 记录成功检查与来源身份，不创建写入提案、不弹确认 |
| 待确认 | 检查成功且发现具体差异 | 冻结差异、来源、目标版本和有效期，展示具体变更后等待用户选择 |
| 部分可更新 | 公司部分 Provider 成功且产生差异，其他来源失败 | 只展示可确定的差异和失败范围；用户确认后只写成功部分，失败部分保留旧值 |
| 检查失败 | 所需来源持续不可用或内容无法核对 | 不生成可写提案、不发布、不推进该来源的成功检查时间；显示重试入口 |
| 执行结果 | 已确认的变更写入完成、无写入或失败/结果未知 | 以 Backend 回执及 Wiki 冷读为准，分别显示新增数量/字段、未变更原因或下一步 |

60 分钟比较的是 Backend 记录的**来源检查时间**，不是 Wiki 页面 `as_of`、文章发布日期或上次打开页面时间。已有待确认提案优先于 60 分钟短路；目标版本变化使旧检查结果失效。取消不写入，重新发起时不得把仍存在的差异说成“无更新”。公司部分成功时，仅已成功检查的来源可使用短路；失败来源下次仍需检查。

## 3. Backend 检查与比较

1. 建立一个 Backend 拥有的刷新检查记录，最少包含目标/范围、目标版本、状态、开始和完成时间、逐来源检查结果、冻结候选、错误类别与关联提案/回执。先核对现有维护存储能否原子复用；不在浏览器 `sessionStorage` 或 Client SQLite 中建立第二套真相。对同一目标/范围实行 single-flight，重进页面可继续读同一任务。
2. 点击后快速返回检查任务或最近检查结果。外部取数在 Backend 后台完成；工作台按钮/页内状态显示“正在检查资料”，不使用持续遮挡页面的加载弹窗，不靠前端反复重新发起任务。检查结果可按任务 ID 回读，页面刷新或工作台重启后仍可恢复。
3. 行业：Backend 从稳定统计局入口发现最新合格表 3 原文，核对行业行，冻结 URL、标题、发布日期、原文哈希和目标版本。先与当前时间线按来源身份比较；已存在则返回无更新。创建提案时复用 Backend 刚完成的检查快照，不再为了转交浏览器来源字段而立即重复联网。确认执行前仍须核对原文身份；确实变化则使提案失效并重新检查、重新确认，不静默写入另一篇。
4. 公司：在确认前读取正式财务/估值 Provider，按字段、报告期、单位、口径、来源时点归一化后与已发布 API 槽位比较。只把实际变化的字段冻结到提案；不得以“请求成功”或重新编译页面代替差异。确认执行时只应用这份候选并校验目标版本/候选有效期，不在确认后才临时取一份用户未看过的数据。缺失、失败的字段保留旧值与原日期；全失败或零差异不发布新 Wiki 版本。
5. 检查记录和维护提案关联；确认、拒绝、执行回执由现有 Backend 维护接口与审计 Owner 保存。无变化的检查结果不伪造“用户已确认写入”回执；写入后回读 Wiki，核对行业时间线新增来源或公司实际变更字段。重复确认不得重复发布。

## 4. 失败、重试与过期

- **临时故障**：连接中断、TLS 握手失败、超时、限流或服务端临时错误，只在 Backend 对该来源做有界重试；建议首次失败后短退避再试一次，仍失败时由同一后台任务延迟再试一次，然后结束为可重试失败。记录尝试次数和失败阶段；用户可以离开页面，不能因为点击多次并行轰击上游。重试总耗时需有上限，实施时用真实来源延迟校准。
- **确定性失败**：来源结构不含对应表 3 行、行业/公司身份不匹配、字段口径无法核验、原文内容或目标版本确实变化，不做网络式盲重试。前两者说明无法核对；后两者重新检查并要求用户看新差异再确认。不得把网络失败标成 `stale_source`。
- **部分失败**：公司各 Provider 独立记录成功/失败，成功且变化的字段可进入部分更新提案；失败字段不覆盖、不更新成功检查时间。行业来源不可核对时整项失败，不追加未经验证的链接。
- **结果未知**：确认请求超时或断连后，先按提案 ID 读 Backend 回执与 Wiki 实际内容；执行已开始时不创建第二提案或重新写入。确认前冻结候选超过建议值 15 分钟或目标版本变化，要求重新检查并重新确认。
- **错误协议**：Backend 返回稳定错误码与阶段（预览/比对/提案核验/执行），日志保留脱敏的目标、来源域名、尝试数和底层异常类别；工作台按错误码显示简短原因与可执行下一步，不按中文错误字符串 `includes` 判断，不展示内部堆栈。

## 5. 工作台交互

- 最近已检查/无更新：按钮旁或顶部轻提示显示“最近检查于 HH:mm，暂无新增资料”；不弹确认。行业如最新来源已在时间线，显示“这条统计来源已收录”。
- 有差异：确认层展示目标、来源、行业将追加的链接，或公司将变化的字段/期次/口径；部分失败同时点明未能检查的部分。用户确认后收起确认层，页内显示状态；完成时顶部提示并可打开回执。取消保持页面原样。
- 检查失败：顶部提示“这次未能检查完，资料保持原样”，提供重试；错误详情可在结果视图查看。失败与无更新不共用绿色成功态。重复点击检查中的任务只打开已有结果，不重新起任务。

## 6. 实施顺序与验证

1. Stock Backend：先补统一检查记录/single-flight、60 分钟短路、来源/字段比较及类型化错误；修正公司全失败仍可能发布的问题。复用现有维护提案的用户授权、幂等与回执，保留两类 Wiki 各自的数据规则。
2. Vibe 工作台与 DSH facade：接检查任务与结果状态，移除行业来源字段经浏览器转送和中文字符串判断；公司/行业共用检查、确认、回执 UI，按各自差异展示内容。
3. 确定性测试：60 分钟内成功检查短路且不请求上游；失败不短路；同对象并发只一任务；无差异无提案/无发布；公司全失败零发布、部分失败仅写成功字段；行业重复来源零追加；预览成功后核验网络失败仍报可重试，原文真变化需重新确认；确认重复/断连回读不重复写。
4. 真实运行：公司、行业各走“无更新、失败后重试、有差异→取消、有差异→确认→冷读回执”；核对 Backend 日志、任务记录、Wiki 前后版本和页面提示。夹具/构建只证明机械路径；真实来源、持久化和视觉由对应运行验收。现用服务不默默重启，部署验收另行安排。

## 7. Out of Scope

- Agent/Jev 自动判断或修改研究主张、成立/失效条件、Topic、关系与其他 Wiki。
- 为公司刷新补抓年报/公告、改行业研究正文、跨对象批量刷新、定时全库抓取。
- 为规避统计局偶发失败而放宽来源身份、哈希、版本或用户确认校验；失败时用旧缓存冒充新检查。
- 现有服务重启、数据迁移或历史资料重写；确需存储变更时在实施前先验证现有 Owner 与回滚办法。

## 8. Stop Conditions

- 检查记录无法在 Backend 现有存储中保证同对象唯一任务、持久回读和幂等：先确定唯一 Owner 与最小持久化方案，不落到浏览器或 DSH 临时状态。
- 公司 Provider 返回值缺少足以比较的字段身份、报告期、口径或来源时点：停止该字段的“有变化”判断，不猜测差异或覆盖旧值。
- 冻结候选无法保证用户看到的内容就是执行内容，或执行后无法以 Wiki 冷读/回执确认：停止写入路径，先补契约与验证。
- 同一行为连续两次补丁仍失败：保存真实请求、Backend 异常类别、提案/回执和 Wiki 前后版本，重新审视 Owner 与协议，不继续叠补丁。
