# 数据归属与 gbrain 退役（讨论记录）

状态：2026-10-09 用户提出、Claude 只读核实并整理，供用户裁决；**不构成实施授权**。裁决后写入 Checklist（两仓共享章「系统职责与数据归属」）并另开 Task。

## 1. 问题（用户提出）

- Backend 定位为以后的云端公共层。不同 Agent 按我们的方法论、工具与模板跑出的结论，只要符合框架、经过验证且边界合理，都应算正确；研究判断属于用户，不属于公共层。
- 因此 Wiki 的研究内容应由 Client 管理；资料原件仍在云端 Backend。
- 不让 Agent 通过 bash / read 等工具直接管理文件：coding agent 的做法不能直接搬到这类产品上。
- 跟踪指标推送、实时资讯分析本质上是常驻长程任务，需要可恢复的运行方式。

## 3. 建议的边界：三层

| 层 | 内容 | 位置 |
|---|---|---|
| Backend（公共、客观） | 资料原件与解析、证据、事实准入、硬关系、行情与计算成果（含 provider 快照）、方法论与模板定义、引用校验服务 | 云端 |
| Client 存储（用户自己的） | 研究判断（原 Wiki 研究块）、议题与跟踪项、研究关联、记忆与画像、页面布局 | 现为本机 SQLite；上云后为每用户一库或按用户隔离 |
| Agent 运行时 | 交互对话；常驻长任务（跟踪检查、资讯分析） | 交互为 DSH；常驻层在 T14 定 |

- 公司页、行业页的系统内容不再编译存储，由个股页 / 产业链页模板在打开时从 Backend 取数组合（T7 / T7b）。

## 4. Client 的写入方式

- 业界区分：Agent 用 read / write / bash 直接改文件，适合开发者自用工具（Claude Code 记忆文件、OpenClaw workspace）；面向用户的产品为 Agent 调业务工具，服务层校验后写数据库并按对象记版本（ChatGPT 记忆、Letta 记忆块、Notion AI）。
- 存储：沿用 Client SQLite（orchestrator 拥有），新增研究对象表；每次写入追加一行修订（对象、版本号、内容、依据引用、作者、时间），不覆盖。T10 的版本、差异、撤回由此得到。
- 写入路径：Agent 只调产品插件提供的业务工具；Client 服务先调 Backend `/refs/resolve` 核验依据，再核对版本号并在事务内写入。产品预设不挂文件工具（不变量 #15）。
- 上云：同一表结构，换成每用户一库或按用户隔离的数据库。

## 5. pi-durable 可借鉴的设计（本地 `pi-mono-main` 6fb2e7815，durable 1.1.0，仍为实验版）

| 设计 | 对应场景 |
|---|---|
| 持久任务：按阶段存检查点，可等待子任务，重启后从检查点继续；任务内 `sleep(until)` 按 Harness 时钟等待 | T12 跟踪检查：每个跟踪项一个任务，取数 → 匹配 → 判断影响 → 写入或提醒，下一次检查时间存进检查点；也可承接知识整理超时问题 |
| 原子提交，先存后显示 | Agent 输出、研究对象修订、跟踪状态同一事务提交 |
| 类型化文档，可选可回溯历史 | Client 研究对象的修订历史 |
| 工具重放语义（只读可重跑，有副作用标记中断） | 现有写入已带 `operation_id` 保证幂等 |
| `requestId` 幂等提交 | 推送只送达一次 |
| 任务图订阅，任务记录带开始/结束时间 | 后台任务状态标准（名册行、阶段按钮、进度卡）直接由任务图投影 |
| 工具与钩子可调用模型（`ToolExecutionApi.models`） | 跟踪任务内的影响判断复用同一模型接入 |
| `pi-server` / `pi-client` / `pi-protocol`：多个客户端挂接同一持久会话 | T16 多渠道（Web、飞书、微信）接同一 Agent |
| SQLite 存储可在云端每用户实例运行（Cloudflare Durable Object） | Client 存储上云形态 |

不借：自带的 read / write / edit / bash 编码工具；在 T14 之前不替换 DSH 运行时（AGENTS：DSH 拥有运行时，不另建执行器）。DSH 是否有调度与持久任务能力仍待核实。

## 6. gbrain 退役顺序（建议）

1. Backend 自存 provider 快照为不可修改成果（与 T3 同一成果链），并从 gbrain `page_versions` 一次性回填。**唯一前置条件**。
2. 搜索改道：事实与资料走 Backend 检索；用户研究内容走 Client 全文检索。
3. 停止系统块编译，公司页、行业页由模板现取数渲染（与 T7 / T7b 合并）。
4. 4 块研究内容及议题、研究关联、记忆、草案迁入 Client 存储，带修订历史（衔接 T10）。
5. 移除 gbrain、`stock_research_gbrain` 数据库与发布管线。

## 8. 用户裁决（2026-10-09）

原话要点：

1. Backend 存放原始资料：Client 端 Agent 调工具收集到的数据都存入 Backend，从某种意义上算知识底座，我们提供检索工具。Wiki 本身也属于知识底座的范畴，但属于 Agent 调用的。我们主要提供方法论、模板与 schema 的设计，属于知识框架。用户的数据存在本地。
2. Client 存储先用本地 SQLite。产品定位为云端 + 客户端：上云是商业模式，提供跟踪与常驻（类似 Memoh）以及平台助手扩展（飞书等）；用户不要上云服务（可选）则免费，模型可自选（DSH 本身支持）。SaaS 版本在云端，客户端在本地。
3. gbrain 按 §6 退役：合理。
4. 常驻长任务层在 T14 评估：合理。

Claude 据此整理的四个概念：

| 概念 | 内容 | 位置 |
|---|---|---|
| 知识底座 | 原始资料、Agent 工具取得的数据（行情、财务、网页快照等）、证据、事实、硬关系、成果；检索工具 | Backend（云端） |
| Wiki | Agent 维护的公司 / 行业知识，供 Agent 调用，不原样展示给用户 | Client 本地（用户确认） |
| 知识框架 | 方法论、页面模板、schema | 产品提供 |
| 用户数据 | 研究判断、议题与跟踪、研究关联、记忆与画像、页面布局 | Client 本地 SQLite |

产品形态：本地客户端免费、模型自选；云端为可选付费服务，承载常驻 Agent（跟踪检查、资讯分析、推送）与平台助手（飞书等）。
