## 2. openclaw 的五条原则与对照

| openclaw 原则 | 含义 | 我们的现状 | 差距 |
|---|---|---|---|
| 没有隐藏状态 | 记忆都是可读可改的文件 | 已符合（Markdown + 记忆页） | — |
| **写入才是难点** | 写入质量决定记忆质量；整理放到后台专门一轮，不在回复路径上 | 每轮整理直接写入画像 / 近期记忆 | 缺“先暂存、跨会话复现后再晋升”的闸门，单轮一句话就进常驻记忆 |
| **写入路径就是安全边界** | 写入时记录来源等级，外部内容结构上不能晋升 | 只有立场，没有“来源等级”；一轮里读过网页后，整理出的内容照样能进画像 | 缺来源等级与“本轮受外部内容污染”标记 |
| 确定性闸门 + 模型在闸门内判断 | 打分、阈值、生命周期是代码；模型只做语言判断 | 整理完全由模型决定写什么 | 缺代码层的准入与容量规则（除条数上限外） |
| 失败不阻塞回复 | 记忆每一步有超时和降级 | 已符合（10 秒超时，失败不注入） | — |

## 3. 建议方向（逐条待确认）

### 3.1 分层（沿用现有载体，不新造存储）

| 层 | 内容 | 写入 | 进入模型 |
|---|---|---|---|
| **核心记忆**：画像 `soul` + 研究主线 `recent` | 稳定偏好；持续问题、关键纠正、未决分歧 | **只经“晋升”写入**（3.3）；用户直接要求（“记住…”）可立即写 | 常驻注入，但按相关度裁剪（3.4） |
| **情景记忆**（新增暂存区） | 每轮整理提出的记忆候选，带来源与对象 | 知识整理每轮写这里，不再直接改核心记忆 | 不自动注入；可被搜索 |
| **知识**：研究记录、议题、Wiki | 不变 | 不变 | 不变（按需工具） |
| **待办触发**（3.5） | “财报出来提醒我看 X” | 议题跟踪项结构化 | 触发时注入 |

### 3.2 来源等级（写入时由代码标注，模型不能在文本里伪造）

- 等级：`owner`（用户在对话里亲口说的）、`agent`（Agent 从用户内容推断）、`untrusted`（来自网页、检索、上传文档、第三方研报等外部内容）、`system`（整理 / 报告等后台任务的脚手架文字）。
- **本轮污染**：一轮里调用过外部内容工具（读网页、外部检索、资讯卡片、上传资料原文）后，这一轮之后产生的推断都记为 `untrusted`。注入隔离（Jev）拦的是“显式指令”，污染标记管的是“被外部内容影响的结论”，两者互补。
- 后台会话（公司研究任务、知识整理、报告）**不产生记忆候选**。
- **防回流**：本轮注入的记忆本身不再被整理成新候选（同一件事被召回一百次还是一件事）。

### 3.3 晋升（后台整理一轮，代码闸门在前）

- 频率：每天一次或累计 N 个候选时，作为 DSH 后台任务运行（沿用知识整理的执行方式）。
- 闸门（确定性）：`untrusted` 与 `system` 候选**直接排除**；按“跨会话复现次数、被召回次数、最近出现时间、是否用户明确表达”打分过线；同对象同主题的候选合并。
- 整合（模型）：把过线候选与现有核心记忆一起交给模型改写——合并重复、用“替代键”淘汰旧条目、不超容量。输出不合格（丢失过多条目、超容量）就退回“只追加”。
- 可回看：每次晋升写一条“记忆变更记录”（改了什么、为什么、来自哪些会话），记忆页可查看与撤回。
- 用户纠正永远优先：被用户改过或删过的条目，后台不得改回（现有规则保留）。

### 3.4 召回（两条路）

- **默认路（零模型调用）**：核心记忆按“与本轮对象的相关度 × 重要度 × 时近”排序后注入，不再全量。本轮对象来自页面、@ 引用、议题绑定（对应 openclaw 的“项目作用域”：跟当前公司 / 议题无关的记忆降权或不注入）。条目可带“触发词”，命中时提前注入，每轮最多 3 条。
- **深查路**：问题里有“上次 / 之前 / 我说过”这类回忆意图且默认路没命中时，Agent 用工具查情景记忆、研究记录与相关会话摘要（沿用现有 `note_list` 等工具，新增 `memory_search`）。

### 3.5 待办触发（前瞻记忆）

- “等半年报出来看万华境外毛利率”“价格跌破某水平时提醒我复核”不存成记忆文字，而是**编译成议题跟踪项上的机器触发条件**：公司新定期报告入库、指定日期、资讯雷达关键词。触发时推送提醒并在议题会话注入该跟踪项。
- 生命周期显式：待触发 / 已触发 / 已完成 / 已取消 / 已过期；默认冷却 24 小时、最多触发 3 次、90 天过期，防止反复打扰。
- 与“不给买卖建议”纪律一致：触发只提示复核某项证据，不生成交易动作。

### 3.6 用户画像的写法

- 条目写成指令式偏好（“回答先给结论，再给依据”“金额默认用亿元”“不要推荐具体股票”），带观察日期与状态（有效 / 已替代）。
- 偏好变化**原地替换**，不追加相互矛盾的两条（研究表明追加式历史会让模型按旧偏好回答）。

## 5. 待用户决定

1. 是否接受“核心记忆只经晋升写入”（会比现在写得更慢、更少，但更准）。
2. 来源等级是否按 3.2 的四级；读过外部内容的轮次是否一律不能晋升。

4. 召回是否从“全量注入”改为“按对象相关度裁剪”。

**结论（2026-09-24 用户）**：① 接受核心记忆只经晋升写入，用户明确“记住…”可直写；② 来源四级，读过外部内容的轮次一律不能晋升；③ **晋升按暂存候选数量触发**（默认累计 10 条，可配置），不按时间；④ 召回按对象相关度挑选；⑤ 前瞻记忆并入议题跟踪项；⑥ 顺序 M1 → M2 → M4，其后 M3、M5、M6。

## 7. 2026-10-08 修订：对照 Memoh 与 grok-bot

背景：用户画像要由"用户在设置里填写"和"系统推断维护"两部分结合；以后接入微信、飞书等渠道时要跨渠道连续（见[降低门槛与产品闭环](降低门槛与产品闭环_讨论记录_2026-10-08.md) §4–§6）。参考代码：grok-bot `source/host/extensions/memory/`（`memory-service.ts`、`memory-synthesis-service.ts`）与 `source/host/runner/sand-memory.ts`；Memoh `internal/memory/`（`memllm` 抽取与更新提示词）与 `internal/agent/runtime/native/prompts/_memory.md`、`_identities.md`。

### 7.1 三者对照

| 维度 | grok-bot | Memoh | 本设计（§3） |
|---|---|---|---|
| 分层 | `profile`（长期：身份、偏好、约束、回复方式）与 `log`（带日期，按月分文件） | 7 层概念文件（偏好、身份、背景、经历、活动、人设、笔记），带置信度、标签、关联，并有人可读的索引 | 画像 `soul` + 研究主线 `recent` + 暂存区 |
| 来源 | `explicit`（用户明确要求）/ `synthesis`（推断）/ `legacy`；**explicit 永不被自动修改或删除** | 模型判断新增、更新、删除或不变 | 来源四级（§3.2）+ 立场（明确表达 / 推断 / 纠正） |
| 删除 | 墓碑：删掉的内容不会再被推断回来 | 直接删除 | 有删除记录，但没有"禁止再推断回来" |
| 写入 | 每轮粗筛后记为证据 → 防抖 15 秒后批量合成 → 每条改动必须引用证据 → 另一次模型调用复核 → 用版本指纹防并发覆盖 | 抽取事实，再与已有记忆比对 | 暂存 → 按数量触发晋升（闸门 + 整合） |
| 时间 | 每天复查一次，"计划中"到期后改为"已发生"，不编造结果 | 记录捕获时间与更新时间 | 无 |
| 召回 | 画像全量注入；近期记忆按"重要度 + 30 天半衰期"排序；**一个会话阶段内冻结快照**，保护提示词缓存 | 按标签与关联检索 | 按对象相关度 × 重要度 × 时近 |
| 跨渠道 | 用户级记忆在多个 Agent 间共享；另有按项目的记忆 | `PROFILES.md` 记录用户、群组与各平台身份；记忆按 bot 隔离 | 单用户、单渠道 |

### 7.2 修订（用户已确认）

1. **画像来源规则（采用 grok-bot）**：
   - 用户在设置"关于我"中填写的内容，以及亲口要求"记住……"的内容，属于 explicit，系统永不自动修改或删除；
   - 系统推断的属于 inferred，可以被新证据更新；
   - 用户修改了推断出来的条目，这条转为 explicit；
   - 用户删除的条目留下墓碑，系统不得再推断回来。
2. **写入必须有据并经复核**：晋升（§3.3）时，每一条新增、更新、删除都要引用证据（会话与轮次）；先过代码闸门，再做一次复核（用另一次模型调用，或确定性校验加模型校验），通过后才写入；用现有的 CAS 版本号防止并发覆盖。仍按暂存数量触发（9 月 24 日结论 ③），可以加一个防抖。
3. **按日期复查**：带日期的条目（"等三季报出来再看"）每天复查一次。到期后改成过去时，不编造结果是否发生。跟踪类的提醒仍然编译为 Topic 跟踪项（§3.5 不变）。
4. **召回时冻结快照**：一个会话阶段内（新会话或压缩之后才重算）冻结注入的记忆，按对象相关度挑选（§3.4 不变），避免每轮变动破坏提示词缓存。
5. **画像分为四类（金融场景）**：水平与表达偏好、持仓与关注、投资风格与约束、纠正。用于调整表达的深浅和措辞，也影响推荐与推送范围。§3.6"写成指令式、原地替换"保留。
6. **边界：记忆只关于用户**。关于公司、行业的认识进 Wiki；跟踪与推送的上下文进 Topic；都不进记忆。这与 M9.3"研究积累来自主动沉淀"一致，也是我们和这两个项目的根本区别。
7. **跨渠道（P4 再做）**：参考 Memoh 的身份映射，把同一用户在 Web、微信、飞书上的身份对应到同一份画像。推送就是某个跟踪项的变化，用户在外部渠道回复时，路由回该 Topic 所在的会话继续，上下文不靠记忆传递。
8. **Jev 的位置待定**：采用"每轮粗筛记录证据、后台批量合成"之后，每轮用 Jev 判断"四个时刻"不一定还需要，可以降为证据粗筛。等影子模式数据出来后决定。

### 7.3 对 §4 实施拆分的影响

- M3：晋升加入证据引用、复核与按日期复查。
- M4：召回加入会话阶段冻结。
- M6：改为"四类画像 + 设置里的'关于我'（用户可查看、修改、删除）"。
