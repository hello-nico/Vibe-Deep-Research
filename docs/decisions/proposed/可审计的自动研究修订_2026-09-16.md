# 决策（proposed）：可审计的自动研究修订

状态：proposed（2026-10-04 用户决定保留为提案；来源 M9.3「实施后新增原则」，2026-09-16 提出，从未实施）。

## 问题

研究判断目前只能在议题会话里、经用户确认后修订。这保证了判断不被越权改写，但也意味着：后台在研究中发现明显的新证据时，只能等用户下次进入议题才会被看到；用户需要逐次确认每一处修订。

M9.3 当时提出：判断不必永远正确才记录，Agent 负责证据优先、中立分析与反证，人和 Agent 共同发现与纠正；用户负责是否采纳和行动。记录不等于采纳。

## 提议

后台可按本轮实际触及的对象，自动修订 Wiki 与已有议题的研究内容，前提是：

1. 经 Backend 正式写入：对象身份、证据引用、权限与版本冲突由代码保证。
2. 同时保留当前版本与可回读的修订历史：原结论与条件、新结论与条件、修订理由、证据引用及版本、来源会话与轮次、提出者、时点、替代或推翻关系。不覆盖错误判断。
3. 用户判断、Agent 推断、已核验事实明确区分；用户反馈改变研究重点，不自动把事实判真。
4. 当前版本与审计记录一致提交；校验失败不宣称写入成功；重试不重复修订；旧快照不能覆盖新判断。
5. 不新增正式议题，不越权改事实与关系层；按需执行，不全库主动重写。

## 与现行规则的冲突

直接冲突：[不变量](../../contracts/invariants.md) 4（所有维护写入要用户确认）与 5（判断只在议题会话修订）。**采纳本提案需要修改这两条**，不能在实施中静默绕过。

## 启动条件（先证明再设计）

满足以下证据后再写成实施 Task：

- 影子模式或日志数据显示：后台确实经常发现应修订判断的新证据，且用户确认环节是主要瓶颈。
- 现有 Backend Wiki 与议题版本历史已盘点，明确缺哪些审计字段。
- 有一个最小验证：保存一条证据有限、标注为推断的判断 → 新证据到来 → 后台修订 → 当前页与历史都能回读，能看出原判断、为何改变、依据与来源。

## 曾考虑的替代方案

- **保持现状**（只在议题会话修订）：最安全，代价是更新滞后。
- **后台只生成修订提案，不直接写入**：用户进入议题时集中确认。改动小，与现行不变量兼容，可作为第一步。
