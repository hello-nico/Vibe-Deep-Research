# 开发工作流范式

本仓库在 2026-09 形成并验证的人机协作开发方式：**用户定方向与验收，Claude 规划与审阅，Codex 实施**。AGENTS.md「Project file protocol」是硬规则，本文说明怎么用、为什么，以及踩过的坑。

## 1. 角色

| 角色 | 负责 | 不做 |
|---|---|---|
| 用户 | 方向与取舍拍板、真实运行与视觉验收、重启工作台、说“可以提交” | 读长篇计划（Claude 给结论与选项） |
| Claude（主线程） | 调研现状、写 Task、审阅回填与代码、合并与冲突、视觉收尾与小修、提交、维护 todo / Checklist | 大块实现（交 Codex）；替用户验收；未经同意提交或 push |
| Codex（可多窗口） | 按 Task 实施、跑自动检查、回填 Task、按停止条件叫停 | 真实验收、合并主线、push |

原则：**谁的判断就由谁做**。数据与接口事实由 Claude 核实后写进 Task；产品取舍给用户选项并附推荐；执行细节留给 Codex 并要求回填理由。

## 2. 文件与各自的 Owner

| 文件 | 只放什么 | 不放什么 |
|---|---|---|
| `human-checklist.md` | 用户确认的决策与验收边界，带日期；新决定注明替代了哪条旧决定 | 计划、进度、未决讨论 |
| `todo.md` | 顺序与未决：执行队列、Claude 待办、已完成清单、延期事项、远期路线 | 决策正文、执行证据 |
| `docs/*_Task_*.md` | 一个有界闭环的完整规格与执行回填 | 其他 Task 的内容、复制上层全文 |
| `docs/README.md` | 文档索引，每个 Task 一行：做什么 + 状态 | 细节 |
| 设计稿（Artifact） | 需要用户看图拍板的交互 | 作为实施依据前未被确认的内容 |

决策先进 Checklist，再被 Task 引用；Task 状态变化同步 README 一行与 todo。

## 3. Task 文档模板（≤ 200 行）

```
# 标题（编号）
状态：日期 + 谁确认 + 待谁实施；执行方只跑自动检查；不提交、不 push（并行线另说）；实施仓库。
权威：Checklist 小节、设计稿、上游 Task（链接，不复制）。
## 1. 目标            一两句，用户能看懂的结果
## 2. 现状（Claude 核实） 文件路径 + 函数名 + 真实数据样例；这是 Task 质量的关键
## 3. 冻结决定         接口、字段、文案、边界；写成可验证的句子
## 4. 范围             改哪些文件
## 5. 验收             执行方自动检查（命令 + 新增测试要点）／ 执行方回填要求 ／ 用户验收（逐步可操作，写预期现象）；执行方不重建服务、不重启本地环境（写明“由用户执行”）
## 6. Out of Scope
## 7. Stop Conditions  什么情况必须停下回填而不是硬做
## 8. 回滚
## 9. 执行回填         Codex 写；Claude 审阅补记（“x.x Claude 审阅与补修”）
```

写 Task 的要点：
- **“现状”必须亲自查**：读代码、查真实数据（如直接请求接口看返回）。凭印象写的规格会让执行方照错的做。
- **冻结决定要可测**：例如“概率 ≥ 0.8 整条隔离，正文替换为……”，而不是“适当隔离”。
- **Stop Conditions 是安全阀**：T3-0 因“需改 DSH 包”按停止条件叫停，省掉了一条走不通的路。
- 不确定的技术路线先做 **技术验证 Task**（原型可丢），结论再决定正式 Task。
- 依赖已知时可**预写**后续 Task（如 T6-c），前序完成即可派发。

## 4. 生命周期

1. **讨论**：用户提需求或问题 → Claude 查现状、给结论 + 选项 + 推荐（“说人话”，先结论后依据）。
2. **拍板**：用户选定 → 先写 Checklist，再写 Task，同步 README / todo。
3. **派发**：给 Codex 一段启动 prompt（Task 绝对路径、工作区、提交规则、并行线提醒、回填位置）。
4. **实施**：Codex 做完回填；遇停止条件就停。
5. **审阅**：Claude 看 diff 与回填，重点见 §6；小问题直接修并记入“Claude 审阅与补修”，大问题打回或另立 Task。
6. **验收**：用户在主目录真实运行（Claude 提醒需要重建 / 重启，由用户执行）。反馈问题 → Claude 定位根因 → 小修直接做，成批问题整理成修复 Task。
7. **提交**：用户说“可以提交” → Claude 给出分笔计划（每笔标题 + 内容 + 不提交的文件）→ 执行 → 汇报提交号。
8. **收尾**：todo 移入已完成、删临时分支与 worktree。

## 5. 并行（多个 Codex 窗口）

- 按**改动文件**分线：互不相交的线可并行；改同一批文件的放在同一条线里串行（如 D → T4-b）。
- Vibe 前端并行线用独立 worktree + 本地临时分支 `codex/<task>`（不 push）；只动一个仓库且无冲突的线可直接在主目录做；只改评估脚本的线不需要 worktree。
- worktree 里 Codex 在分支上提交；**回填写主目录的 Task 文件**，避免多份副本。
- 合并由 Claude 做：先备份主目录全部改动（补丁 + 未跟踪文件），再把分支改动叠加到主目录**先不提交**，用户在主目录验收；提交时优先 cherry-pick 保留 Codex 原提交，其余按主题分笔，并逐字比对备份确认没有丢改动。
- 工作台与 Backend 重建只由一方执行（用户），避免互相回收进程。

## 6. 审阅要点

- 规格对照：冻结决定逐条核对，偏差要么是执行错，要么是**规格写错**——后者要更正 Task 原文并注明。
- 语义副作用：新增状态会不会被旧读取方误用（例：未核验“假设”混进研究关联列表，会被 Agent 当成已确认）。
- 真实数据回归：接口类改动用真实对象请求一次，看节点、连线、字段是否合理；**补修之后也要再跑一次**（曾因“优化查询”删掉关系来源，真实数据当场暴露）。
- 边界与失败：失败时是否降级并说明，而不是静默当作“没有”。
- 测试断言写死实现细节时，改实现要同步改断言，并说明原因。

## 7. 心得

1. **先定位根因再修**：看不到根因（如首卡空白未复现）就不改样式；能复现、能指出代码位置才动手。
2. **用框架给的扩展点，不用 CSS 硬挪**：“保存为记录”先用 CSS 调位置失败，改挂 DSH 的 `assistant-actions` 插槽才对；动手前先查插槽和接口。
3. **系统不替用户做判断**：过期报告只提醒、不隐藏、不自动重生成；Agent 只提议，写入等确认。
4. **区分“不能做”与“不该在这里做”**：DSH 包不打补丁，走不通就换方案（T3 方案 B）而不是改依赖。
5. **一个位置表达一个状态**：状态标在能处理它的控件上（报告过期点在「图文报告」分段），不堆在名字旁边。
6. **验证先于实施**：Jev 先做中文效果验证、按用途裁决，只把验证通过的用途产品化；没通过的写明条件留待下一轮。
7. **自动检查 ≠ 验收**：执行方只报它跑过的；真实交互与视觉由用户确认，文案里不把“测试通过”说成“功能可用”。
8. **小步快提交**：一批验收完就提交，再开下一批设计；未提交的改动越多，合并越难。
9. **每次回复给出改动文件清单**，让用户随时知道动了什么。
