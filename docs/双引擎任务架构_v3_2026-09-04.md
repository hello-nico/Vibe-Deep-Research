# 双引擎任务架构 v3 · 2026-09-04

> 状态：架构决策已重新校正；M0 任务协议 / 路由器、M1 Quick v1 执行器与 M2 后端任务入口 / UI
> 已在活动仓库本地实现，并完成独立 Codex 审计闭环。M3 Deep 适配器尚未接入，当前不属于可发布状态。
> 本文是 v2 的版本化后继，不覆盖历史文件。v2 中引擎生命周期、共享工具、
> Chat Completions 传输层等工程结论仍有效；本文取代它对 Quick 产品语义和验收点的定义。

## 1. 结论

Vibe Research 有三条执行路径，不是两个完整研究引擎二选一：

| 路径 | 责任 | 模型 | 典型任务 |
|---|---|---|---|
| Browse / Deterministic | 浏览、登记数据源刷新、确定性计算 | 不调用 | 看页面、刷新数据、计算指标 |
| Quick | 在已备齐的文本材料中定位相关段落 | 直连 API | 按目标筛选已有材料段落（v1） |
| Deep | 开放取证、跨来源验证、多步长任务 | Codex Harness | 从零调研、补证据、处理冲突、六阶段研究 |

当前 `DirectStageAgent` 能用直连 API 执行六阶段，它属于 **Direct Deep 实验适配器**，
不是 Quick。这批代码保留，但不再用它定义 Quick 的验收标准。

## 2. 四个维度必须分开

| 维度 | 当前取值 |
|---|---|
| 用户入口 | UI / CLI / API / MCP |
| 用户模式 | Auto / Quick / Deep |
| 执行路径 | deterministic / quick / deep |
| 模型与付费 | ChatGPT 订阅 / API key / 兼容网关 / 本地模型 |

`provider` / `model` / `apiKey` / 底层 `engine` 不进 `ResearchTask`。任务先按语义路由，
然后才由目标适配器选取可用的运行时配置。

## 3. 两层契约，不再混用一个 Engine 概念

### 产品层：ResearchTask / Task Router / ExecutionEngine

- `ResearchTask`：描述目标、任务类型、取证范围、流程形状、安全材料引用和期望输出；
  Browse / Refresh / Calc 还必须携带类型化 `operation`，不能靠自然语言猜要调用哪个程序。
  它不携带原始正文、文件路径或调用方自报的 `materialState`。
- `TaskMaterialResolver`：在服务端逐条核对材料存在性、类型与授权，返回绑定版本的解析结果；
  `ready / partial / missing` 只从这份结果派生；`ready` 还必须绑定材料版本和文本 / 非文本模式。
- `QuickMaterialLoader`：只在路由进入 Quick 后读取已授权版本，并交付由可信服务端解析器预切的
  净化文本段落。Quick 执行器不接收磁盘路径，也不从整篇正文猜段落边界。
- `TaskOperationRegistry`：用真实查询 / 端点 / 计算注册表校验确定性操作是否存在、参数是否可执行。
- `TaskRouter`：只在服务端启动时注入上述两个可信依赖。每次 HTTP 请求只能提交任务，
  不能提交 resolver、operation registry 或 `ready` 结果；材料解析后的判定部分保持纯函数。
- `ExecutionEngine`：消费已路由任务，产出统一事件流；恢复运行必须同时核对不可变运行 ID 与
  绑定任务、材料版本的路由指纹。Quick 和 Deep 各有一个适配器。

### 六阶段内部：EngineLifecycle / AgentRunner

现有 `engine.ts` 和 `runner.ts` 只负责「已经决定跑六阶段研究以后，
怎么准备引擎环境并执行单个 stage turn」。它们是 Deep 的内部实现，不是产品层路由器。

## 4. Auto 路由规则

1. `browse_data` / `refresh_registered_data` / `calculate` 直接走确定性程序。
2. 只有 `locate_passages` 满足以下全部条件时走 Quick：服务端确认材料全部 `ready` 且为文本、
   最多 16 份、只用现有证据、单步工作流、输出格式为文本。
3. 材料缺失或部分缺失、需要开放式找新证据、或需要多步调查时走 Deep。
4. 显式选择 Quick 但任务不符合时，当场拒绝并说明原因，**不静默改用 Deep**。
5. 显式选择 Deep 可以将有界分析升级为深度执行。
6. 确定性任务不因界面当前选了 Quick / Deep 就浪费模型额度。

路由只用结构化任务元数据，第一版不让 LLM 判断该走哪条路，避免账单、速度和执行保障在用户不知情时改变。

## 5. 统一格式不等于统一份量

三条路径共用 `TaskEvent` 与后续 `TaskResult` 信封，但产物按任务类型可选：

- Browse 可以只返回页面数据或确定性计算。
- Quick v1 返回模型筛选的完整材料段落与绑定版本的引用；产物明确标成
  `model_selected_passages / non_exhaustive`，并在正文提示“不是摘要，也不代表材料全貌”。
- Deep 返回报告、证据、计算、冲突、manifest 和完整运行记录。

「共用 schema」不得被解读成「Quick 也必须跑六阶段并写完整报告」。

## 6. 借鉴结论

实时查看了三个成熟开源实现：

- [Vercel AI SDK Provider Registry](https://github.com/vercel/ai/blob/main/packages/ai/src/registry/provider-registry.ts)：
  借鉴「上层通过注册表获取能力，不把 provider 写进业务任务」。
- [OpenAI Agents JS Runner](https://github.com/openai/openai-agents-js/blob/main/packages/agents-core/src/run.ts)：
  借鉴「Runner 与 ModelProvider 分开，每次运行单独传 maxTurns / signal / session」。
- [LangGraph JS](https://github.com/langchain-ai/langgraphjs)：它解决更重的持久化图执行与恢复。
  本仓库已有六阶段状态机、事件账本和 validator，引入它会形成第二套状态真理源。

决策：**不增加新运行时依赖**；只借鉴边界形状，在现有 Core 上建最小契约。

## 7. 与行业 Plugin 的关系

`ResearchTaskKind` 只表达跨行业通用动作（浏览、定位段落、摘要、比较、抽取、深研）。
行业 Plugin 后续以可选契约声明：

- 这个行业允许哪些 Quick 任务；
- 每种任务可以看哪些资料和工具；
- 输出 schema 与 validator；
- 页面入口与 eval 用例。

不恢复一套独立旧项目，也不把 Plugin 改回无类型 YAML 配置。

## 8. 推进顺序与验收

### M0：任务协议与纯函数路由（本轮）

- [x] ResearchTask 不夹带 provider / model / apiKey / engine。
- [x] API 原始对象必须经严格解析；执行器只消费路由器封好的 task + decision，二者不能错配。
- [x] Quick 的材料状态由服务端解析与授权结果派生并绑定版本，不能由调用方伪造或复用旧结果。
- [x] 三类确定性任务均携带类型化操作参数，并必经服务端操作注册表端口验证；真实注册表适配在 M2 接线。
- [x] Auto 可确定地路由到 deterministic / quick / deep。
- [x] 每个路由决策带机器代码和可展示理由。
- [x] 显式 Quick 不符合时拒绝，不静默换引擎。
- [x] 现有六阶段入口与行为不改。
- [x] 定向测试、类型检查、Core 纯净度、全量串行回归与 Codex 四轮审计闭环。

### M1：真正的 Quick v1 执行器（本轮）

- [x] 只实现 `locate_passages`；摘要、比较、解释、抽取、翻译、资料问答在没有独立校验器前，
  Auto 一律走 Deep，显式 Quick 当场拒绝。
- [x] 不进六阶段状态机；不开放 Shell、工具循环、任意文件读取或联网搜索。
- [x] 一次模型请求；模型只能从系统提供的段落编号中选择，不能生成答案或引文。
- [x] 段落由服务端解析器预切；每份最多 512 段、每段最多 2,000 字符、总正文最多 40,000 字符。
- [x] 加载结果必须与路由绑定的 kind / id / revision 一致；复制或伪造的路由决定不能执行。
- [x] 结果映射回系统持有的完整段落，展示绑定版本的引用、真实 provider / model 和非穷尽提示。
- [x] 交付前经过同一合规 gate。
- [x] 定向测试、类型检查与 Core 纯净度通过；七轮问题发现 / 修复审计后，收敛复审为
  `No actionable P1/P2 findings`。

这里刻意不把“一次模型请求选出若干段落”包装成摘要：模型可能选择性遗漏，当前没有确定性校验器
能证明语义完整。扩大 Quick 能力必须逐项新增产物契约和机器可判定的验收，不靠提示词承诺。

### M2：后端任务入口与 UI

- [x] 实现真实 `TaskMaterialResolver / QuickMaterialLoader / TaskOperationRegistry`：材料从本地研报库按
  `id + revision` 绑定读取；页面查询、注册数据源刷新和确定性计算均走现有真实注册表。
- [x] 计算参数校验新增只验证、不执行公式的 `calc/cli.py validate` 契约；真实执行支持取消、超时和输出上限。
- [x] 新增统一 `POST /tasks`，不暴露 `--engine`。调用固定为两段式：先以 `execute:false` 获取路由，
  再携带 `expectedRouteFingerprint` 执行；材料变化时返回 `route_changed`，不透明换路线。
- [x] 路由请求拒绝模型配置；执行请求只有目标仍为 Quick 时才解析直连模型配置，避免把 Quick 凭据带入 Deep。
- [x] 「我的研报」显示 Auto / Quick / Deep、选择材料、任务目标、路由理由与结果；上传、删除、选材和任务执行互斥。
- [x] M2 的 Deep 明确显示“只完成路由判断，未启动长流程”，不伪装成已经执行。
- [x] 旧六阶段 `/research` 入口保留兼容。
- [x] 全量验证：orchestrator 653 项（652 通过、1 项 Windows ACL 在 macOS 跳过），desktop 29/29，
  Python 577/577；两端类型检查与前端生产构建通过。真实浏览器完成临时材料导入、Deep 路由、未执行提示、
  无伪结果和测试资料清理。最终 Codex 复审：`No actionable P1/P2 findings`。

### M3：Deep 适配器

用产品层 `ExecutionEngine` 包装现有 Codex 六阶段编排。只做适配，不复制状态机。

### M4：Direct Deep 的去留与容器验证

当 M1-M3 都稳定后，再决定 `DirectStageAgent` 是否作为高级兼容能力对外开放。
在没有 Codex 二进制与包的环境里真跑前，不宣称 Direct 路径是独立轻量部署。

## 9. 当前已知缺口

1. M3 尚未把现有 Codex 六阶段编排包装成产品层 Deep `ExecutionEngine`；因此 M2 的 Deep 只路由、不执行。
2. `run.ts` 的 Direct 分支仍无条件调用 `sdkCodexVersion()`，会探测 Codex 二进制。
3. Direct 六阶段未共享 `AGENTS.md` / 行业 skills 的方法论注入，仍只能叫实验性 Direct Deep。
4. Quick v1 只支持在已提取文本中定位完整段落；摘要、比较和开放研究没有机器校验器前仍走 Deep。

上述缺口闭环前，不合并、不推送、不改公开产品口径。
