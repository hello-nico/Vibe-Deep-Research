## 1. 目标

一个只读接口给出某议题的“证据墙”：墙上有哪些对象、对象之间有哪些连线（硬关系 / 研究关联 / 用户假设），每条线能回到依据。并让用户能在议题内直接写“假设”连线，之后经提案确认升格为研究关联。

## 2. 现状（2026-09-24 Claude 核实）

- 议题（`app/services/research_topics.py`，文件在 `workspace/research/topics/`）：`subjects`（如 `company:600900.SH`、`industry:sw2:801161.SI`，也混有“境外收入占比”这类非身份文字）、`observation.fact_refs / source_refs / relation_refs(claim:)`、`judgment.basis_refs`（`claim:` / `evidence:` / `source:` / `lookup:` / `page:<slug>@<hash>`）。
- 研究关联（`app/services/research_links.py`，`workspace/research/links/index.json`）：来源仅 `note:` / `result:`（及议题发布的 `wiki_material`），目标仅 `topic:` 或 Wiki 页；提案 → 确认两步；无状态字段。现有 8 条。
- 硬关系：PostgreSQL `claims`（`claim_kind=relation`），`WorldModelStore.local_graph`（`/entities/{id}/graph`）按单个根实体遍历。实体身份 `company:600900.SH`；NBS 行业 `industry:nbs:<官方名>`，对应 Wiki `industries/nbs-<简称>`（`wiki/constants.py`）；公司 Wiki `companies/600900-sh`。当前数据很少（长江电力：持股湖北能源、运营白鹤滩水电站；后者端点为 Asset，不属硬关系端点）。

## 3. 冻结决定

### 3.1 墙上的对象（节点）

从议题收集，去重后每个节点给 `ref`（产品对象引用：`companies/…`、`industries/…`、`themes/…`、`comparisons/…`、`document:<32位>`、`note:…`、`result:<32位>`）、`kind` 与 `origins`（为什么在墙上，可多个：`subject` / `basis` / `source` / `relation` / `link` / `hypothesis`）：
- `subjects` 中可解析的公司 / NBS 行业 / 申万行业身份 → 对应 Wiki slug；非身份文字忽略。
- `basis_refs` 的 `page:<slug>@…` → slug；`source:` / `evidence:` → `document:<文档ID>`；`claim:` → 该 Claim 的两端（若为公司 / NBS 行业）。
- `observation.source_refs` 同上；`observation.relation_refs` 的 Claim 两端。
- 以该议题为目标的已确认研究关联的来源（记录 / 成果 / 发布材料）。
- 本议题研究关联与假设的两端。
- 标签不在此接口解析（前端对象登记层负责）；节点 ≤ 60，超出按来源优先级（subject > basis > relation > link/hypothesis > source）截断并给 `truncated: true`。

### 3.2 连线

每条线：`edge_id`、`kind`（`hard` / `link` / `hypothesis`）、`from`、`to`（节点 `ref`）、`label`（中文）、`basis`（依据引用列表），总数 ≤ 200。
- **硬关系**（只读）：墙上公司 / NBS 行业节点**两两之间**的当前有效硬关系（`valid_at = known_at = 现在`）。谓词只取 standard §2：`subsidiary_of` 隶属、`owns_stake_in` 持股、`supplies_to` 供应、`customer_of` 客户、`produces`（对端为行业时）所属行业、`upstream_of` / `downstream_of` 上游 / 下游；Asset 等其他端点不出现。`basis` 为支持该边的 `claim:` 列表（前端点开走现有 `/claims/{id}`）。在 `WorldModelStore` 新增按实体集合一次查询边的方法，不逐节点遍历。**不向墙外扩展邻居。**
- **研究关联**：两端都在墙上的已确认关联（含本 Task 新增的对象 ↔ 对象关联）。以议题为目标的“记录属于议题”不画线（已体现为节点 `origins: link`）。
- **用户假设**：本议题的假设连线，`label` 为用户那句说明，另给 `unverified: true`。
- 硬关系读取失败（PostgreSQL 不可用等）时，其余照常返回，`sections.hard = "unavailable"`；正常为 `"ok"`。不静默当作“无关系”。

### 3.3 研究关联扩展

- **端点放宽**：来源与目标均可为公司 / 行业（`companies/` / `industries/`）、资料（`document:<32位>`）、记录 / 成果；目标仍可为议题。存在性校验沿现有 `_target_resolvable` / `_material_exists` 思路补齐资料与 Wiki 页。
- **状态**：新增 `status`：`hypothesis` / `confirmed`。现有记录无此字段即视为 `confirmed`（读取规则，不迁移数据文件）。
- **创建假设**：`POST /wiki/research-links/hypotheses`：`topic_id`（必填，须存在）、`from`、`to`、`note`（1–200 字）。**由用户直接创建，不经提案**；同议题同一对端点（无序）只允许一条假设；不经 Agent 工具开放。
- **撤回假设**：`POST /wiki/research-links/hypotheses/withdraw`：`hypothesis_id` + `topic_id`；只删除 `hypothesis` 状态记录。
- **升格**：沿现有 `propose` → `confirm`，`propose` 增加可选 `hypothesis_id` 与必填（升格时）`basis`（≥1 条 `claim:` / `evidence:` / `source:` / `page:` 引用，格式校验）；确认后该记录 `status` 改为 `confirmed`，保留原 `note`、`created_at` 与 `promoted_at`、`basis`、`proposal_id`；拒绝则假设原样保留。
- 研究关联仍**不是**硬关系：不写 `claims`，不进图遍历。

### 3.4 接口

- `GET /wiki/research-topics/{topic_id}/wall` → `{ topic_id, nodes, edges, sections: { hard }, truncated }`；只读，不触发任何外部取数、模型或 Jev 调用。
- Vibe `desktop/dsh/finance-ui/research.mjs` 代理放行：GET `…/research-topics/{id}/wall`；POST `/wiki/research-links/hypotheses`、`/wiki/research-links/hypotheses/withdraw`。

- 公司 / 行业实体身份与 Wiki slug 无法确定性互转（需要猜测或模糊匹配）：停止，回填样例。

- 研究关联端点放宽会改变现有提案 / 确认语义或现有数据含义：停止回填差异。
