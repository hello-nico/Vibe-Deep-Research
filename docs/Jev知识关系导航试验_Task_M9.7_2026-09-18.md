## 1. 目标与确认边界

产品决定 Owner：[Human Checklist](../human-checklist.md)「Jev 判断接入边界（2026-09-20）」。
复用 M9.1/M9.2 后台交接与过程记录、M9.3 研究连续性和维护契约、M9.6 资料版本引用。

用户强调以广义贝叶斯分类器理解 Jev：给定充分研究上下文，区分明确假设/类别，返回结构化判断供程序使用。
概率依赖输入与问题定义，不代表未提供事实的真值，不跨用途合并为统一可信度。
目标：主 DSH Agent 完成分析后，将后台固定判断工作交给 Jev；代码将有效结果映射到 Backend 服务，完成知识维护并留下审计记录。
判断明确且服务支持的工作直接处理，不要求每项工作再启动完整生成式 subagent；需要补查、发现新候选或文本修订时才转交它。

撤销研究前材料排序、阅读裁剪和压缩收益闸门：上下文不足时不能判断哪些材料不值得读，降低优先级同样可能导致漏读。
本 Task 不改变主线检索顺序、阅读范围或用户 @ 引用。

## 2. 一个后台闭环，三类判断

主 DSH 分析完成 → 现有交接 Owner 固定轮次快照 → 准备上下文与原文 → Jev 结构化判断 → 代码分派 Backend 服务 → 记录结果。

| 工作 | Jev 判断 | 后续处理 |
|---|---|---|
| 判断复核 | 原文对结论是支持、冲突还是不足？新证据是否挑战旧边界？ | 记录疑点、绑定证据、登记补查；必要时转 subagent 修订 |
| 研究连续性 | 与哪个已有 Topic/问题相关？属于重复、补充、修正、分歧或独立问题？ | 关联研究记录、更新内容或保存 Topic 建议，沿用既有采用规则 |
| 实体与关系整理 | 实体类型、指代、同一性；关系类型、方向、否定、条件及有效时间 | 原文绑定、身份与提取候选校验，经正式服务持久化 |

三类均在本 Task 范围，按现有服务就绪程度逐项闭合，不再将后两类排除出首期设计。
复核针对影响知识维护的判断，不逐句认证；原文支持不等于现实成立。
连续性相关不等于用户意愿；自动维护与新建 Topic 建议沿用产品既有授权边界。

## 3. Owner 与执行位置

| Owner | 职责 |
|---|---|
| 主 DSH Agent | 主线取证、分析和回答，交接本轮结果；不逐次决定是否调用 Jev |
| 现有后台交接 Owner | 唯一触发、生命周期、预算、中止和追踪；不新增并行 finalize/第二执行器 |
| Backend | 原文、证据、身份、版本、校验及正式写入服务；Jev 凭据与外部请求收口 |
| Jev 适配 | 输入与问题 schema、请求和返回校验、错误分类；不预拆独立包或复制协议 |
| Jev | 基于给定上下文分类，不自主执行服务或授予事实准入 |
| 生成式后台 subagent | 承接补查、开放式提取或文本修订 |

沿用成功轮次交接，固定 source session/turn 与版本；下一问不清空已交接快照、不取消已有维护。
主线回答和下一问不等待维护完成；关闭过程面板不中止任务，取消沿用现有生命周期。
不新增用户可见 Jev Agent、主模型常驻工具、平行索引或正文存储。

## 4. 输入与判断契约

按判断准备必要上下文，不为节省 token 裁掉语义前提：
- 本轮问题、用户反馈、最终分析及来源轮次。
- 涉及的结论、实体/关系候选、相关 Wiki/Topic 内容及版本。
- 对应文档 revision/hash、Block/原文跨度、章节、说话人、期间、否定和条件。
- 必要前序研究和纠正记录，以及未能取得的上下文。

主模型总结不能替代原文。缺少必要材料时补取、分解问题或标为不足；超预算不得静默删证据后继续执行。
各类判断分别定义封闭答案集合及版本，记录目标、输入快照、分类与概率、模型/问题版本。
接口错误、未检查、证据不足、无关联是不同状态；概率不作为写入权限。
校验候选 ID 属于输入，拒绝缺项、重复、未知类别及过期版本；不接受任意 URL、方法名或可执行代码。
实施前核对实际 Jev primitive 与产品 schema 的映射，不假设结构化分类等于任意 JSON 文本生成。

### 实体与关系：候选发现和判定分开

复用主分析过程或现有提取流程的原文跨度、实体和关系候选，交 Jev 分类、消歧与判定。
新名称、新实体和未定位关系不能因不在选项中被排除：保留未知/需发现候选，由现有提取能力或生成式 subagent 补充。
验证须覆盖候选发现漏项，不能只在预设正确实体的样本上宣称完成抽取。
相同实体对不代表同一关系；方向、谓词、条件、时间与证据必须保留。

## 5. 判断到 Backend 行动

实施时核对并填写「分类 → 现有服务 → 参数来源 → 校验 → 结果记录」映射，不虚构路由。
判断明确且服务支持的结果直接调 Backend，无需主模型再次转述或逐项批准。
需要新文本、补证或重新分析时才转生成式 subagent；不足不能冒充成功。

- 正式写入走现有 Evidence/提取/关系/Wiki/Topic 服务，不绕过 validator 直写数据库或文件。
- Wiki/Topic 修订沿用既有自动维护、草案和采用契约，不因 Jev 擅自扩大或缩小权限。
- 幂等绑定轮次、目标、判断契约与输入版本；重试回读已完成操作，版本冲突重新判断，不覆盖新状态。
- 每个成功操作立即留结果；后续失败记部分完成，不重复创建实体、关系、关联或修订。
- 允许未来证据纠正判断；保留旧版本、原证据、修改者与修订原因，不覆盖审计历史。
- 不要求证明每次判断正确才记录；服务校验成功也不等于语义正确。

## 6. 用户可见与审计

沿用「我的研究」后台任务与只读过程面板，展示对象、状态、结果、疑点和补查/修订入口。
可回到来源对话、原文、Wiki/Topic 和具体修订；不灌回主线生成第二条回答，不混入普通聊天历史。
复用任务/沉淀记录保存输入绑定、分类、分派操作、Backend 回执、失败原因、耗时用量，不另建台账。
区分无新增、待补查、成功、部分完成、失败、取消；API 失败不能显示为无增量。

## 7. 接入、预算与参考

Backend 持服务端凭据并限制发送内容；不复用用户全局 CLI key、不在浏览器放密钥、不 spawn 全局 CLI。
真实调用前明确数据类型、提供方、费用及超时/重试预算；工程方根据样本提出具体值，用户确认数据发送和成本边界。
超时、限流、schema 错误不转成业务分类；有界重试或转既有后台处理，不阻塞主线。

参考 TypeSafe [System One](https://docs.typesafe.ai/concepts/system-one)、[引用核验](https://docs.typesafe.ai/cookbooks/citation_check)。
本机 typesafe-mcp、jev-compaction 可参考协议适配、调用与错误记录；CLI 传输不构成本产品设计依据。
旧 compaction fake 测试不证明金融判断质量，压缩比例不充当语义质量闸门；neo4jev 保留为历史参考。
实施前固定模型、协议与两仓基线，不把历史参考的版本和性能当永久事实。

## 8. 实施步骤与验收

1. 核对后台交接、候选来源、Backend 服务和过程面板，明确复用点与真实接口缺口。
2. 分别定义三类输入/分类 schema/服务映射，标记直接处理与 subagent 升级，复核写入边界。
3. 人工核对真实研究样本，覆盖否定/预测、上下文不足、纠正、关系方向、未知实体、跨轮次接续。
4. 同快照比较现有后台 subagent 与 Jev 路径，校准/验收集分离；先旁路，再在批准范围验证服务写入。
5. 分别报告误报/漏报、候选发现漏项、错误关联/写入、人工复核量、升级率及总时延费用，不只看分类命中率。
6. 验证幂等、重复交接、版本冲突、部分完成、取消、中断和下一问并行，证明只有一个交接 Owner。
7. 真实验证 DSH 分析 → Jev → Backend 回读 → 后台记录 → 后续纠正；mock/schema 测试不代表闭合。

质量阈值用于离线验收；运行时检查可验证的契约和状态，不虚构每批语义收益。
三类分别验收；某类未通过保留既有处理，不因其他类别通过自动启用。

## 10. Stop Conditions

- 缺乏充分上下文、原文或候选：记录缺口并补查，不编造。
- 服务缺失或需要改变权限/数据发送范围：明确缺口与选择，不绕过 Backend。
- 两轮调整仍无实际收益：复核问题定义、上下文和候选来源，不继续堆阈值。
- 审计不可回读、幂等/版本失效、错误写入不可追溯：停止对应写入路径。
