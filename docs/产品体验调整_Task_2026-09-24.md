## 1. 调整点

### A. 资讯雷达问一条，却灌进整栏列表（已核实）

用户截图：资讯雷达 · 公开新闻（关注 19 只、共 60 条）问助手首条气泡是整屏东方财富 URL；输入区只钉了一条「有色金属行业资金流出…」。用户判断：输入太多导致卡顿，信息稀释太重。

**根因（不是模型胡写）**：发送时宿主把整栏快照写进**同一条用户消息**，DSH 原生气泡原样显示。

1. `Intel.tsx` `WatchlistFeed` 最多 60 行（`MAX_ROWS = 60`），经 `feedPageContext` → `buildFeedListSnapshot` 做成 `page.context`。每行是 `时间 公司（代码）：标题（完整 URL）`。东方财富 unify 链接很长，60 行轻易顶到 `PAGE_SNAPSHOT_LIMIT` 16_000 字。
2. `FinanceAiDock.send` 把 `page.context` 整份交给 `bindAssistantPrompt`；`apply.ts` `startAssistant` 再 `face.prompt([{ type: 'text', text: bound }])`。绑定文是「页面快照 + @ 读取 + 身份与问题」，没有展示/模型两套文本。
3. 快照自己写「链接正文在 @ 后由宿主读取，不在此重复」，却仍带每条完整 URL。@ 了一条时，模型同时拿到 60 条标题+URL，再加这一条正文（`fetchCitedUrl`，单条最多 24_000 字）。
4. 同构：`buildInvestmentNewsSnapshot`、A 股公告同一 `feedPageContext`。大盘快照是结构化数字，问题不同，不按本条改。
5. `visibleUserPrompt`（`taskTrajectory.ts`）已能从绑定文抽出「用户问题：」之后的原文，只用于「保存为记录」。M9.9 写明「面板用 `visibleUserPrompt`」本包不做，所以气泡仍是整段绑定文；原生 Markdown 再把括号 URL 折成一堆断链，看起来更乱。
6. 新闻行没有点选追问；chip 来自用户 @。`useAiPageObjects` 把本栏每条 URL 登记为可 @ 对象（正确）；Dock 不会在普通发送时自动把 60 条都加成 chip。

卡顿有两层：气泡渲染超长 Markdown；若误 @ 多条，发送前会对每条 `POST /documents/fetch-url`（并行、单条 15s 超时、合计 80_000 字）。

### C. 缺口项点「现金分红」却打开依据失败（已核实路径，未回读该页引用）

用户截图：个股研究页「关注点与缺口」写明四项是快照标出的缺口、补齐前不作替代估算；「现金分红」旁是「必录基础事实缺失」。点「现金分红」后右侧「查看依据」显示「这条依据暂时无法读取，请稍后重试。」并给「重新读取」。页脚来源是同花顺快照。

**产品矛盾**：正文已经说这是缺口，点击却按「有依据、暂时读失败」处理。缺口 ≠ 临时故障。

路径（代码，未对该页做 `/wiki/refs/resolve`）：

1. 该段是研究页 Markdown（`WikiSections` 对非财务/估值块走 `KnowledgeText`）。正文里的 `claim:` / `evidence:` / `source:` / `provider:` / `lookup:` 被 `remarkCitationMarks` 收成链接，再变成不带 snapshot 的 `EvidenceLink`，发送 `POST /wiki/refs/resolve`。
2. `resolveEvidence`（`lib/evidence.ts`）未 resolved 时，`provider:` 与其它引用本有不同说明；`EvidenceCard` 的 `.catch` **丢掉具体错误**，一律写成「暂时无法读取，请稍后重试。」网络失败、来源不完整、版本对不上也是这句。
3. 财务事实块若走 `FactList` 且 `source === 'provider'`，会带本地 snapshot，不请求 resolve，应出现同花顺披露而不是这句。用户看到的失败句，说明点到的是**无 snapshot 的引用**（Markdown 引用最贴截图结构）。
4. `wikiFacts.ts` 的同花顺三表路径不含 `cash_dividend`。M7 已记现金分红等字段未覆盖。页上标缺口与取数覆盖一致；错的是把缺口标题做成可点依据。

实施前须对该公司页 markdown / block.refs 看「现金分红」实际绑的是哪条 ref、resolve 回什么。未回读前不写死「引用坏了」还是「缺口不该能点」。

**Claude 回读结果（2026-09-24，万华化学页）**：研究页 `gaps` 块第一项即 `{"metric": "现金分红", "reason": "required_basic_fact_missing"}`，块 refs 为一组占位 lookup（如 `lookup:company:600309.SH:metric:cash_dividend_or_dividend_per_share:latest`）。对这些 lookup 调 `/wiki/refs/resolve` 返回 `status: "pending"`（只有 lookup_id，没有数值）——连已有数据的净利润 lookup 也是 `pending`。研究页 Markdown 本身没有“关注点与缺口”标题，截图中的这一节更可能来自图文报告（Lieflat HTML 把缺口项也挂了 `data-ref`）。结论：**缺口项绑的是“待取数”占位引用，不是坏引用**；错在两处——报告把缺口项做成可点依据，`EvidenceCard` 把 `pending` 与网络失败都写成“暂时无法读取，请稍后重试”。18 家公司研究页都有“现金分红”缺口，属普遍问题。

### D. 大盘成交额 / 板块资金盘后空白（已回读接口）

用户截图（约 21:23–21:29）：全市场成交额 TOP20、板块资金趋势榜、资金轮动流入/流出四块都是「暂无数据：可能是非交易时段或数据源暂时不可用」。同屏「更新于」仍有时间。

**不是休市没数。** 2026-09-24 21:31 对本机 `POST /page/review`（不带 refresh）与 `POST /fetch em_turnover_rank`：

- 上下文：`session_phase=post_close`，`review_date=2026-09-24`（今天已收盘，显示今天）。情绪、涨停池、炸板、昨日涨停、龙虎榜均为 `ok`，证据在，最早 18:45。

成交额榜不在 `review` 查询里，页面另走 `api.turnoverTop()` → `em_turnover_rank`，同一套过期+失败逻辑。
