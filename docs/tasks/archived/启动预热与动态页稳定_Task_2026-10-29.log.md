### 4. 波动原因

1. 公告 `list_announcements` 的 `_SUPPLEMENT_DEADLINE=8s`：远程按公司 `read_cached`，超时取消的不入缓存，下一次再等 8s；`poll.py` 抢源。这就是公告卡 5–12s。
2. 行情 15s TTL 过期后，页面等 1.7s 的源站取数（单飞）。
3. `loadFilingRows` 原顺序：公告 → 行情取简称 → Wiki。公告卡必须等行情。
4. 浏览器 6 连接：冷 page-research 每家约 7s，16 家排队到十几秒；热了以后不再是主因。

## R1（pi1-cold，未重启）

工作区：Stock `/.worktrees/pi1-cold`，Vibe `/.worktrees/pi1-cold`。未提交、未重启。

### 原因

1. 关注页每家走 `page-research`。GET 里 `new_material` 会现场拉公告源（东财 limiter，httpx 默认 30s）。预热同时在拉同一 key，页面单飞等这次现场计算，三次重建都落在 30.8–31.3s。
2. 容器 `logging.root.level=WARNING` 且 `handlers=[]`。原 `logger = logging.getLogger(__name__)` 的 info 不会进 `docker logs`。现网确认：`app.services.read_warmup 0 False 30 []`。
3. 现网热态 `page-research` 0.04s、quotes 0.07s，说明慢的是冷路径现场拉数，不是 Wiki 锁 8s（那会是 8/16s 而不是 31s）。

### 改法

- GET `new_material(..., live=False)`：只 peek 内存/磁盘，不等 pending、不 `build()`。未命中返回 null。
- 预热仍 `live=True` 走 `read_research` + `new_material` + 数据包 + 对账 + 公告 + 报告期。
- 日志：`print` + `uvicorn.error.read_warmup`，格式 `read warmup: start N companies` / `read warmup: 600011.SH 7.3s ok` / `read warmup done 84.2s`。

- **R2（退回）**：「GET 未命中就返回 null，只靠预热补上」意味着只有被预热的用户才能看到「新资料」提醒，而预热目前只覆盖本机用户，上云多用户后其他用户可能一直看不到。改为一条对所有用户都成立的规则：读取未命中时立即返回 null（不等待），同时在后台触发一次拉取（单飞，同一 key 只拉一次，失败不缓存），下一次读取就能命中。预热照常保留，作为提前填好缓存的手段，但不再是必需的。
