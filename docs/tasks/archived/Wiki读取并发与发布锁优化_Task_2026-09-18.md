# Wiki 读取并发与发布锁优化

状态：已实施（2026-09-18）；实施、验证与事件记录见 §8，待用户 review 与产品验收。

## 1. 目标与权威

- 用户要求解决 Wiki 正文、目录、相关材料读取竞争发布锁的问题，同时保护发布完整性。
- 遵守两仓 AGENTS.md、README 与现有发布/恢复契约；Backend 是 Wiki 与关系读取 Owner，DSH 不新增执行链。
- 目标：读读可并行、读取不启动 GBrain CLI、同请求索引只加载一次、忙碌原因可判断。
- 本轮不承诺发布期间始终可读；返回明确忙碌优于读取半成品。旧版本持续可读属于后续存储设计。
- 开始前记录两仓 HEAD、相关 diff 和运行服务版本；保护用户及其他 Agent 改动，不自行提交、push 或重启产品服务。

## 2. 已核实的入口

Stock-Research 路径相对其仓库根目录：

- `backend/app/services/wiki_publish_lock.py`：固定 key 88179901；每次连接后获取排他 advisory lock，wait=True 最长等待 120s。
- `backend/app/services/wiki_refresh.py`：发布前恢复、读 existing page、compile/publish 共用排他锁；此边界必须保留。
- `backend/wiki/gbrain_adapter.py`：existing_page 每次加载 pages.json、校验 Markdown 哈希；pending 存在时拒绝读取。
- 同文件 related_pages 顺序调用 get_links/get_backlinks 两次 CLI；page_update_times 已有只读 SQL 接缝。
- 同文件发布顺序：pending → Markdown → sync/extract → 链接对账/验收 → pages.json → 清 pending。
- `backend/app/api/v1/wiki.py`：`/industries/nbs`、`/pages`、`/pages/read`、`/pages/related`、GET `/page-drafts/research` 等目前持排他锁。
- `/reports` 的 GET 通过 _current_page 读页，目前未统一进入读取锁；需一起检查，避免遗漏竞争窗口。
- Vibe `desktop/src/verticals/finance/components/ResearchKnowledge.tsx` 已独立请求相关材料，但后端排他锁仍会串行化这些请求。

## 3. 实施顺序

### A. 基线与锁调用清单

1. 枚举所有 brain_publish_lock、existing_page、索引/关系读取及 publish 调用者（含宿主与脚本），标明读/写、进程及现有保护方式。
2. 不以 HTTP GET/POST 区分锁：真正发布、恢复以及读后编译发布必须排他；校验草案、保存报告等先逐个核实契约，本轮默认保留原排他边界。
3. 增加最小结构化计时：操作名、锁模式、wait_ms、hold_ms、结果；读取路径增加索引/正文/SQL耗时与 CLI 次数。
4. 记录无发布时单读、多读并发以及受控发布竞争的基线。不要输出连接串、正文、凭据或模型原始内容。

### B. 共享读取锁与失败契约

1. 在现有锁模块提供明确读取入口，底层共用连接、获取/释放实现，不复制第二套锁管理。
2. 读锁使用 pg_advisory_lock_shared / pg_advisory_unlock_shared，继续使用 key 88179901；写锁保持排他模式。
3. 保持现有 brain_publish_lock 的默认写语义、wait=False 行为及测试模式开关。禁止全局替换为共享锁。
4. 读取锁等待初值 2s；保持现有发布等待策略。区分连接失败、锁等待超时、查询超时；不要把所有异常改成 busy。
5. 统一 API 失败结构：HTTP 503，detail 至少有 code、message、retryable；锁竞争用 wiki_publish_busy，并带 Retry-After: 2。
6. 已遗留 pending 使用 wiki_publication_pending，说明等待后台恢复；不让 GET 自动修复/发布，不诱导用户无限重试。
7. 哈希不一致、数据库不可用等保留独立原因；对外不暴露路径、SQL、连接串，内部保留诊断类别。
8. 异常/超时必须释放连接和已获得的锁；避免共享锁升级为排他锁或嵌套新连接获取导致自锁。

### C. 相关材料移除 CLI

1. 查安装版 GBrain 源码/数据库 schema，核对 get_links/get_backlinks 的 source、关系类型、删除状态、方向与排序语义。
2. 在现有 GBrainAdapter 中用参数化只读 SQL 查询双向链接；优先一次查询合并，设置有界 statement_timeout。
3. 保留自身过滤、去重与现有可见性语义；不能擅自过滤掉已有关系类型，也不能因同 slug 跨 source 产生错链。
4. 查询及正文/标题版本读取仍在共享锁内，保证发布不会穿过；保留 pending 检查。
5. 标题以已接受页面为准；正文不可读时沿用明确降级。不得把失败伪装为空列表。
6. 明确稳定排序、total、offset/limit 的语义；SQL 分页之前必须完成决定可见性的过滤，避免总数与分页不一致。
7. 不新增关系副本，不增加通用 SQL 工具，不改生产 GBrain schema。真实结果与旧 CLI 做同数据对照。

### D. 批量读取与缩短持锁区间

1. 同一请求加载一次索引；增加请求级批量读取接缝，复用 existing_page 的身份、哈希、compiled_spec 校验。
2. `/industries/nbs`、`/pages`、`/pages/related` 共用该路径；单页及报告 GET 也统一一致性保护。
3. 在共享锁内完成 pending 检查、索引/必要 Markdown/关系/更新时间读取和校验，形成独立内存结果。
4. 释放锁后做纯渲染、序列化等；不能在解锁后继续懒读文件或返回关联可变缓存。
5. 标题搜索仍需遍历时如实保留，不引入未经验证的早分页。只消除重复索引解析，不更改搜索与排序含义。
6. 暂不增加进程间缓存或连接池；若测量发现连接成本仍占主导，在本文记录后再决定，不顺带搭新基础设施。

### E. 产品读取反馈

1. 沿用现有页面布局、扫描加载与刷新反馈；相关材料独立加载，不成为正文完成的前置条件。
2. 刷新同一页遇 busy 时保留已显示内容并提示稍后重试；切换对象不能显示上一公司的正文冒充新页。
3. 首次加载忙碌显示“资料正在更新，请稍后重试”；pending 显示暂不可用/恢复中，不能显示无资料。
4. 读取桥与 DSH 工具保留结构化失败原因，核对 researchRead、代理及 BackendRequestError，不新增常驻工具。
5. 仅必要的 UI 反馈修改；不重做报告、知识页或任务面板，不引入无限自动重试。

## 4. 验证与完成标准

- 单元回归：共享/排他 SQL及配对释放、锁超时分类、连接失败分类、pending 拒绝、哈希校验、批量索引加载次数。
- 关系回归：双向、去重、自身、同 slug 不同 source、删除页、正文缺失、稳定分页、失败非空结果伪装。
- 使用隔离测试数据库、临时 Wiki 根目录和真实 PostgreSQL 锁，跨进程验证；mock 锁不能作为并发验收。
- 测试两个读者同时持锁；写者等待读者退出；读者等待写者并在 2s 附近返回明确 busy（允许环境调度误差）。
- 发布暂停在 Markdown 已写但索引未提交时发起读取，不能得到混合版本；完成后读取新完整版本。
- 发布进程中断后确认连接锁释放，但 pending 仍阻止半成品读取；现有恢复流程完成后可读。
- 连续并发读期间发布能获得执行机会；记录等待时间，检查是否存在长读拖延或饥饿。
- 同一固定数据集对比旧 CLI/新 SQL；若当前 GBrain 环境不可运行，标记此项未验收，不以 fixture 替代。
- 前后各至少 20 次同条件读取，记录并发量、页数、冷/热状态、p50/p95、wait/hold/SQL/解析耗时，不预写提速倍数。
- 性能硬性结构标准：在线 related 读取 CLI 次数为 0；单请求索引最多加载一次；无发布时读者不因排他锁互相串行。
- 产品测试正文和相关材料并行、busy 后手动重试、同页刷新保留正文、切换对象与卸载取消、原错误详情透传。
- 运行 Stock 发布/恢复/目录/关系/报告相关测试，Vibe 相关前端测试与 typecheck，git diff --check。
- 报告检查使用真实数据库还是 fixture；部署、真实模型、浏览器验收单列，未经执行不得称闭环完成。

## 5. Out of Scope

- 不缩短实际发布事务、不拆成每页写锁、不绕过 pending 或哈希校验。
- 不实现旧版本快照、版本指针切换、缓存服务、第二关系库或新研究执行器。
- 不改 GBrain 发布/链接提取语义，不更换 GBrain 版本，不新增市场/研究工具。
- 不重启现用产品、不在生产写入测试页、不提交或 push；需要部署时交付明确命令与预期影响。

## 6. Stop Conditions

- 无法确认安装版 GBrain 链接 SQL 与原 CLI 等价，或需要 schema 迁移才能实现。
- 发现任一生产 publisher 绕过排他锁，导致共享读锁无法保障一致性。
- 发现锁嵌套/升级或跨数据库连接导致互斥不成立，先核对 Owner 和调用链。
- 性能问题主要来自长发布，而需求要求发布时立即读旧版；需另行确认快照存储方案。
- 需要改变关系可见性、分页含义或发布恢复契约；先记录证据和选择，不自行改变产品语义。
- 同一行为两次修补仍失败，停止补丁循环，回到锁/快照/查询契约分析。

### 8.4 SQL 等价性证据

- 语义核对（安装版 0.48.4.0 源码 `src/core/ops/links.ts` + `postgres-engine.ts`）：本地可信 CLI 走 unscoped 臂——无 source 过滤、无隐私过滤、仅要求 from/to 两端 `deleted_at IS NULL`；返回行无 title 字段（旧代码 title 恒回退为 slug，再由 API 用 existing_page 覆盖）。新 SQL 保持同语义：无 source/link_type 过滤、两端软删除排除、`f.slug <> t.slug` 与 Python `target != slug` 双重自链排除、按 target 去重保首次（出边先于入边）。
- 同数据对照：`scripts/compare_related_sql.py` 对 40 个真实 slug（容器内钉住版 CLI vs 新 SQL）：`{"checked": 40, "mismatches": 0, "nondeterministic": 0}`。旧 CLI 行序本无 ORDER BY（未定义），新 SQL 以 `ORDER BY direction, target` 明确稳定排序；total/offset/limit 语义不变（先过滤去重后分页）。

### 8.5 测试与性能

- 单元回归：`backend/.venv/bin/pytest -q tests/wiki/ tests/test_wiki_page_candidates.py tests/test_wiki_publish.py` → 155 passed, 7 skipped。
- 全量 backend：692 passed, 5 failed；5 个失败为 `test_real_evidence_artifacts` 本地文档工件缺失，在改动前基线（stash 验证）同样失败，与本任务无关。
- 真实锁并发（`STOCK_RESEARCH_GBRAIN_SMOKE=1` + `stock_research_gbrain_test`，跨进程 spawn）：5 项全过——双读者同时持共享锁；读者持锁时写者 wait=False 立即 busy；写者持锁时读者 2s 附近返回 busy（实测窗口 1.8–4.5s 内）；写者等待读者退出后获得执行并阻塞新读者；发布进程被杀后连接锁由服务端释放、pending 仍拒绝半成品读取、现有恢复流程完成后可读新完整版本。
- pending/混合版本：Markdown 已写、索引未提交时读取抛 `PublicationPending`（API 映射 `wiki_publication_pending`），不返回混合版本；恢复后读到新完整版本。
- 性能（20 次/路径，热态，companies/000001-sz，旧路径经 docker exec 驱动容器内 CLI）：
  - related 旧：p50 10927ms / p95 11026ms（2 次 CLI，每次约 5.5s）；新：p50 27.1ms / p95 38.2ms；在线 related CLI 次数 0；SQL 查询 1 次/请求。
  - pages 列表旧 p50 12.6ms（基准脚本未含旧排他锁连接成本）vs 新 p50 22.7ms（含共享锁连接约 10ms）；列表路径收益在并发不串行与索引单次解析，非单读延迟。
  - 初次验收的“单请求索引加载 1 次”仅覆盖批量方法，Review 发现列表端点实际加载 2 次；本轮改为按前缀批量读取，完整端点测试确认 1 次。以上性能数字为修复前记录，未重新测量。
